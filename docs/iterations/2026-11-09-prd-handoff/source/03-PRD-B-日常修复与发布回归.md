# PRD B：日常修复与发布回归

版本：1.0；日期：2026-11-09；状态：可进入本地开发。产品约束：使用量少，主要由一人维护。现有后台是基础，不重新建设一套评测平台。

## B0. 目标、范围与成功标准

两条主路径共用同一份运行、问题、用例、配置和结果：

**日常：运行记录 → 具体问题 → 修改 → 候选复测 → 对照确认 → 按需沉淀用例。**

**发布：候选版本 → 一键运行固定历史回归集 → 看变化和待核验项 → 满足预期 → 沿用原发布方式上线。**

首期成功以能完整走通两条路径为准：不手抄运行 ID、不重新粘贴已有历史、不为修一条反馈先创建正式评测任务、不把运行成功当作质量通过、不用每次重新组题。

核心范围：已有入口精简与关联、实际候选执行、版本化用例与默认回归范围、批量执行和新旧比较、少量必要人工复核、测试与上线版本关联。zero/few 作为现有对照页扩展，不建设独立实验后台。

## B2. 信息架构与最小交互

保留现有导航。日常主要使用“运行记录”；发布主要使用现有“回归”页扩展后的“发布回归”。用例、Prompt、Skill 仍用原页，按上下文直达，不增加六个管理中心。

### B2.1 运行记录列表

继续使用待审核、需修改、已通过、全部筛选。保留主题、创建时间、轮数、运行状态、审核状态和问题数量。进入具体会话后自动定位尚未处理的问题轮次；不能按标题猜目标轮次。正式评测问题通过来源类型关联展示；若聚合则以实际问题标识去重，保留原记录。

### B2.2 原问题卡

默认可见：原问题、必要历史入口、原回答、原审核意见、期望行为、关联修改/候选、最近验证结论。主要操作沿用或精简为“调整”“用候选复测”“查看对照”“确认解决”“加入回归”。高级 Trace、原 ID、所有版本和历史尝试折叠展示。

新标记问题时只要求一句“哪里不符合预期/希望怎样”；允许同一输入框表达两者，标签自动建议但可修改。已有反馈不要求重新补齐字段才能开始。

“调整”可选择 Prompt、程序文案/代码、资料或检索问题。对无法在线编辑的代码显示所属能力和关联提交入口，不伪造可保存的 Prompt。优先从原路径自动定位，不要求维护者先懂全部平台结构。

### B2.3 对照区

原答案与候选答案并排，窄屏上下排列；默认显示回答与引用变化、实际使用版本、复核结论。展开查看查询/证据、Skill/模式、耗时和已有可获取成本信息。缺字段显示“未记录”，不补造历史配置。

显示本次模式：“固定材料表达/任务试验”或“正常全流程复测”。前者不证明检索和路由改善；后者可能重新取证，应显示材料变化，不能把差异全归因于 Prompt。

### B2.4 发布回归页

默认显示保存的回归集、待测候选版本和最近已接受基线。选定候选后主按钮“一键回归”；已准备好后无需重选用例和任务。可展开调整范围、必达问题和历史版本。

执行中显示完成数、运行中项、技术失败、待人工项；刷新页面仍能回到原批次。完成后优先列“新退步”，再列“已修复”“已知问题仍存在”“待核验/受阻”和普通保持项。报告可导出结构化数据与可读文本，便于下一次跨主机交接。

## B3. 日常小迭代的完整规则

1. 从真实运行某一轮查看问题。自动携带原输入、此前文字历史、来源会话与 run、已有审核、附件/资料关联。
2. 保存候选或关联明确代码/资料改动。候选必须是固定可引用版本；试验不改变线上全局。
3. 选择验证模式。默认正常全流程复测用于判断真实问题是否解决；已有表达对照继续可用，用于定位回答组织问题。
4. 启动新运行；原回答、原审核、原 run 不覆盖。验证结果关联原问题与实际候选。
5. 系统按改动范围建议少量相关保持样本。局部概念 Prompt 默认 FIX-02 + KEEP-02；案例合并包括 KEEP-01 + 完整 KEEP-03。共享路由/公共约束变化则扩大回归。
6. 维护者判断“符合 / 仍需修改 / 待核验”，可补一句依据。技术失败不能选择为有效解决依据。
7. 按现有方式启用修复；只有验证但未启用时显示“验证符合，尚未上线”。完成上线关联后可确认解决。已有直接核对入口仍可用，但需记录方式和依据，不能伪装成自动执行。
8. 适合长期记住的问题可一键生成用例草稿或关联已有用例，自动带入原输入、必要历史、反馈和验收点。短暂故障与重复反馈不强制生成新题。

本地开发可独立完成候选验证，不依赖生产启用。问题状态与发布状态分开，见 B6。

## B4. 发布回归的完整规则

### B4.1 默认范围与版本

复用同一用例库，首期三种标签视图：常用质量、底线检查、按需专项。默认发布回归集保存为可引用的用例版本列表，常用质量含本批八条（KEEP-03 是一个三轮脚本），再加入已准备好的少量底线检查。

同一编号默认一个选定当前版本，发布批次开始时冻结清单；不能把 34 条发布版本当作 34 道独立题，也不能直接以最高数字版本替代人工选定的有效版本。历史版本保留且可查。

附件和资料不齐的旧用例可进入列表并显示受阻，不准默默跳过。只把实际选入且有效的测试计入本次执行范围；范围调整和缺项在报告中可见。无需先重新审核全部 27 个编号才能开展当前开发。

### B4.2 候选与基线

批次绑定明确候选配置及代码提交/构建。基线是上次明确接受的结果，或首次由维护者明确选择的已有结果；没有旧基线时显示“首次建立”，不得编造历史通过结果。

归档答案可用于历史比较，不强制重跑所有旧版本。若补跑旧版本，标记为“本次重现”并保留环境差异。缺旧模型/资料时不能声称精确重现；不要求随机模型逐字相同。

本批五条需修改答案是修复前对照，不是合格示范；三条通过会话保留原审核通过属性，但本次候选仍需按验收点检查。

### B4.3 一键执行和多轮

调用现有实际问答执行入口，不能另写一套只对测试题返回固定答案的实现。候选配置由内部受控入口传入，正式用户请求不能随意指定未开放版本。

同一用例内按顺序执行，每轮保存独立新 run；多轮后续历史使用本次新回答。FIX-05 是固定历史的第二轮复现，带原来的两条消息；KEEP-03 是整段新执行，两者模式不能混用。

执行遇到人工步骤停止当前用例，标明 blocked_step/待人工及已完成步骤；缺附件、指纹不匹配同样准确停止相关部分。其他独立用例可继续，不因一题人工步骤卡住整个批次。RG04 的第 4 步停止要求保留，不擅自跳到该用例后续步骤。

初期低并发（默认 1，可按现有执行器能力调整），保存批次和执行项状态。重复点击或浏览器刷新不重复启动同一请求；服务重启后能识别中断。重试产生新的尝试记录，只重试选定失败项，不覆写原记录；不可自动重复造成无限调用。

### B4.4 判定与报告

先做能可靠自动判断的工程检查，如版本命中、上下文、附件指纹、确定性数值、来源关联存在、无遗漏步骤。来源是否真正支持专业结论、是否跨场景外推以及新知识解释正确性，按需要人工确认。不能以“有引用”“模型输出了评分”直接判定专业正确。

每项保存技术状态、质量结论、专业核验状态和判定依据，不能合成一个含糊的绿色状态。首次输出可标待复核，一键执行不自动假定所有文本答案通过。

不要求维护者每次重新填写所有审核意见。报告优先呈现变化、失败和必要人工项；对答案正文、实际证据内容及验收标准均未变化的项目，可沿用原核验依据并明确标注“沿用”，同时执行本次工程检查。内容或证据改变、原审核范围不覆盖本次内容时，不能自动沿用专业通过；模型可辅助标变化，不能伪造人工结论。

| 原结论 / 本次结论 | 报告分类 |
|---|---|
| 通过 / 不通过 | 新退步，优先展示 |
| 不通过 / 通过 | 已修复 |
| 不通过 / 不通过 | 已知问题仍存在 |
| 通过 / 通过 | 保持 |
| 任意 / 尚未判断、技术失败或缺材料 | 待核验或受阻，不能计通过 |
| 没有可用原结论 | 新增用例/首次结果，单独显示 |

统计报告提供清楚分母：共选择多少用例、自动执行完成多少、判定通过/失败多少、待核验/受阻多少。按会话用例和步骤数分别统计；21 轮不算 21 道独立审核样本。首期不要求单一综合分，不把少量题的比例解释成全平台准确率。

### B4.5 发布判断与上线关联

满足本次明确必达问题、已通过的重要能力无不可接受退步、必须人工核验项目已有结论，才可接受报告用于发布。历史已知问题单列；不必每次清零，但本次必达项、关键事实/数值/引用问题不能被平均分抵消。

若有例外，保存具体未达项、理由和接受人；不能悄悄把失败改为通过。只留下与真实发布有关的简单决定，不引入多级审批。

上线继续使用已有部署/配置启用方式。回填或自动取得实际生效版本与时间，关联报告；首期不新建发布平台。部署版本和测试版本不同，报告显示不匹配，不能复用旧测试的“已验证”标记。配置、代码或资料再变更需要相应范围重新验证。

报告被接受后可明确选为下一次基线；不随每次运行自动替换。回退沿用现有机制并记录实际版本；回退后从正常入口核对实际使用版本。

## B5. 数据关系：逻辑要求，不指定物理表

优先使用已有模型，名称可映射；本表不代表线上数据库结构。

| 对象 | 必需逻辑信息 |
|---|---|
| 来源运行 | 原会话/轮次/run，用户输入，必要历史，旧回答、原路由/Skill，来源和附件关联，实际版本（已有则保留） |
| 问题 | 来源运行/正式执行之一或两者，反馈原文，期望，四状态，关联尝试、复核、已解决依据 |
| 候选引用 | 不可变 Prompt/Skill/示例版本、可取得模型/检索/数据/代码版本，变更说明；无法取得明确 unknown |
| 验证尝试 | 来源问题、模式、请求候选、实际解析候选、材料快照/变化、新 run、技术状态、质量结论、复核依据 |
| 用例版本 | 来源、输入、固定历史或顺序脚本、资料/附件要求、验收点、审核范围、分组、当前使用指针 |
| 回归集/批次 | 冻结用例版本清单、基线、候选、执行项和尝试、状态、结果分类、汇总与发布决定 |
| 上线关联 | 测试报告、已接受候选、实际部署/生效版本、时间与差异 |

来源 run ID 与会话 session ID 不是同一个字段；本批两者长度和格式不同，必须正确保留。历史缺数据使用 missing_fields 列出，不能以当前配置填补成当时事实。

快照优先保存可重现输入及证据引用/必要片段和内容摘要值；不得复制登录令牌或服务密钥。批量导出只包含开发需要的案例内容与溯源标识。

## B6. 状态规则

继续复用旧问题四状态：待处理 → 处理中 → 待复测 → 已关闭。复测仍有问题可回处理中；关闭后复发可重开，保留历史。

额外展示的“验证符合/待核验”“尚未上线/已上线”是关联验证与发布的事实标签，不增加新的问题状态机。候选验证符合但未上线时，日常线上修复问题一般保持待复测并显示标签；正式工程问题按既有关闭语义适配，不强行批量改历史状态。

技术执行使用已有执行状态，并能区分 queued/running/completed/failed/blocked/interrupted 等必要情况；质量结论独立。已有“运行正常”的历史会话仍可“需修改”，这是正常组合。

确认解决需明确选择有效验证或填写直接核对依据；真实线上修复再关联实际启用版本。创建新验证不自动关闭；已关闭不删除历史反馈和失败尝试。

## B7. 导入、历史与离线开发

本包 JSON 是自定义交接格式，不是已验证的线上导入格式。开发侧编写薄适配器导入隔离的本地开发数据库；可映射现有模型，不直接请求生产写入。

导入可重复执行而不重复造题，以包版本与来源会话/目标轮次或脚本键识别。生产标识保存在 source_* 字段；本地实体用独立 ID/命名空间，不能把本包数据冒充新的线上运行。

保留五条原始需修改、三条原始通过；候选新结果全为空/未运行。通过会话无文字意见时记录“会话通过、已审到第 n 轮”，不要伪造赞扬或专家评语。其余未标记轮次不自动判错或判对。

旧正式问题和真实会话反馈先核对是否已有共同标识；有则直接复用，无则做关联/聚合。禁止按同名标题粗暴合并；KEEP-01/03 必须独立。后续确需数据迁移，保留来源和迁移对照，新增字段默认兼容旧记录。

本地无真实知识库可运行录制或模拟证据的流程测试，界面和报告明确标注 simulated；不得将其结果作为真实检索与专业内容验证通过。

## B8. 权限、异常与维护成本

沿用后台现有登录和开发者权限，不新增角色体系。读写与候选执行都由服务端校验；候选只能在授权测试上下文使用。两条候选并行测试不得互相修改全局状态。

原 run 已删除、旧资料缺失、附件不同、模型版本未知、执行超时等显示具体缺项和仍可执行部分。原问题反馈作为只读来源保留，不因本地导入或复测覆盖。超时或中断保存已完成步骤，不能显示整题通过。

维护者不新增日常巡检任务，不要求手动维护多个能力标签体系；标签和相关用例由已有 Skill/模式/来源自动建议。统计默认简单计数，成本信息仅复用已取得数据；首期不追加复杂看板。
