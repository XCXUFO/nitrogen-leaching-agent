# 开发顺序与验收清单

版本：1.0；日期：2026-11-09。本文帮助接手主机在无法访问生产数据库时开始开发，不替代对真实材料与线上版本的最终核对。

## 1. 先完成一次本地盘点

在实际源代码库查清下列映射，记录路径/现有接口/复用方式即可，不要求另建管理文档平台：

| 位置 | 要确认的内容 | 默认处理 |
|---|---|---|
| Skill 注册与路由 | 七项现有 ID、AI/工具/程序类型，是否已有外搜 | 优先保留现有实现和兼容标识 |
| Prompt 装配 | 全局表达层与任务规则在哪拼接，版本如何解析 | 在真实装配处增加任务范围，避免仅改编辑页 |
| 原问题验证 | source_run、历史、附件/资料怎样进入运行，候选能否传入 | 原入口复用，只补缺项 |
| 会话审核与正式问题 | 是否同源、标识怎样关联、四状态语义 | 聚合/关联优先，避免按标题合并 |
| 用例与执行 | 草稿/冻结版本、脚本类型、fixture、独立执行接口 | 用薄适配映射交接数据 |
| 回归执行器 | 多轮、人工步骤、失败/重试、基线保护是否已实现 | 先单题与三轮最小试跑，再做批量 |
| 现有部署 | 代码提交、配置启用、生效版本怎样取得 | 继续使用原方式，不另造发布平台 |

未知供应商、表名、字段、API 和服务器版本不得凭文档猜成事实。若现有实现已满足要求，以复用和验证为主。

## 2. 建议实现顺序

### 阶段 1：离线复现与候选传递

导入本包八条会话及原反馈，建立本地来源关联。先走通 FIX-02 的日常问题页及 FIX-05 的两条历史带入。复用现有 Prompt 版本和左右对照，明确范围；候选进入实际执行后，结果回到原问题。验证不修改全局、原 run 与审核不覆盖。

可交付标志：无需生产数据，在本地就能看到正确原题、反馈与旧回答，保存一个任务 Prompt 候选，并观察真实使用的候选版本。依赖模型不可用时，可用标注的模拟调用验收界面与状态，但不能称回答质量通过。

### 阶段 2：概念与新手回答策略

增加概念业务能力，梳理专业问答、必要澄清和能力介绍；保留真正缺参的追问。用 FIX-02、KEEP-02、FIX-05 检查。capability_guidance 按代码实际能力更新程序文案，正常入口复问验证。

可交付标志：概念短语可以先答；新手指代不被无谓追问阻塞；能力说明准确，旧历史仍可查。专业内容待材料核验处明确保留。

### 阶段 3：案例合并

统一案例入口和上下文，保留两旧 ID 适配、四种任务模式、粘贴文字/表格解释。用 KEEP-01、KEEP-03 完整三轮、材料解释和比较验证。不得丢失来源、单次/合计、推荐量与效果证据边界。

### 阶段 4：联网与检索充分性

把本地取证和外部取证作为共享能力接入真实任务调用。用 FIX-03 测基础解释，用 FIX-01 定位首轮检索/材料问题；同时测超时、无结果、正文不足、来源冲突和只允许本地资料的情况。先在本地离线模拟测试契约，再接真实服务验证实际来源。

### 阶段 5：固定回归集、一键执行和报告

冻结用例版本清单，复用旧独立执行与基线机制；先单题，再 KEEP-03 三轮，再 RG04 的人工停止行为，最后批量执行。实现变化分类、必要复核、基线不覆盖、失败项定向重试和实际发布版本关联。

本阶段可与阶段 2—4 的界面开发交错进行；候选解析、执行结果和问题关联先稳定。不必等所有专业材料齐备才开发报告；缺材料项准确标记即可。

### 阶段 6：轻量 zero/few 对照

在现有对照页增加示例随版本保存，用同一材料和问题分别运行。只比较当前任务相关题，记录示例来源、逐题变化及其他变量。先验证“能准确比较”，再判断是否保留 few-shot。

## 3. 首期必须完成与后续范围

## 5. 验收矩阵：回答与专业内容

| 用例/场景 | 可以先自行判断的行为 | 仍需真实材料支持的内容 |
|---|---|---|
| FIX-01 菜地 N2O | 没把短语当不完整问句；检索与材料缺口可查；先答可支持部分 | 菜地规律、数值口径和支持程度；未新增黄金答案 |
| FIX-02 WHCNS | 第一段先介绍，再引导；无不必要追问 | 模型用途/组成/局限的具体表述 |
| FIX-03 光合作用 | 相关领域判断、真实外搜发生、正文与链接可查、解释直接 | 基础定义/机制和实际来源是否支持 |
| FIX-04 能力说明 | 程序文案更新正常入口生效；没有空承诺 | 按本地代码与配置确认真实开放能力，无需农业专家逐句判断 |
| FIX-05 新手应用 | 保留历史，先说明可理解的用途，必要时再澄清 | 具体应用不超出当前平台和材料能力 |
| KEEP-01/03 案例 | 找到相关对象、有来源、三轮承接、无证据不宣称更优 | 真实案例做法/数值/用量/效果是否与正文一致 |
| KEEP-02 氮素淋失 | 短语先解释、表达可理解、条件不乱外推 | 定义和研究事实是否准确 |
| NEW02 / 数值组合 | 字段、单位、并列、文件位置、历史承接；两个子任务不丢失 | 一般机理的证据与适用性；不得当成本次峰值确定成因 |

验收不是要求外部专家反复检查每项工程行为。只有新增专业结论、原材料争议或负责人无法判断的内容集中核验。原已通过样本保留其结论与核验范围，不因本次开发自动要求全部重审，也不将其扩展为全面专家认证。

## 7. 完成定义与移交回执

本地开发完成时给出以下实际结果：

1. 对照本包说明完成了什么、复用了哪些模块、哪些验收仍受材料阻塞。
2. 实际代码提交/构建、迁移与兼容策略、配置启用和回退方式。
3. 两条路径的本地演示结果及关键测试结果；模拟与真实执行分开。
4. 八条真实问题的逐项新结果、来源/配置变化、仍需专业确认处。
5. 发布回归报告，实际选择的用例版本/候选/基线和未完成项。
6. 实际部署时将报告与生效版本关联；在此之前不能把“开发完成”当作“线上已修复”。

## 8. 可直接复制给接手开发者的任务说明

请先阅读本包00、01，再执行两份PRD。当前是用户少、主要一人维护的农业问答平台；复用既有后台，不建设多套新中心。两条主路径是从运行记录修日常问题，以及大版本前一键跑历史回归再上线。

生产数据库在本机不可见，data中的8条会话和21轮原问答、5条评价及3条通过记录是需求事实来源；按源ID和目标轮次复现，不能按标题猜问题。FIX-05目标是第二轮且要固定带两条历史；KEEP-03必须顺序执行完整三轮，不能与同名KEEP-01合并。已通过不等于逐字黄金，需保留证据边界，避免无提示换案例。

先核对代码已有能力，导入隔离本地数据并复用source_run、Prompt版本对照、独立执行、用例冻结和基线。补齐真正进入运行的候选配置、结果回原问题、当前使用版本与固定回归集。业务上新增概念/联网、合并案例、按任务封装Prompt、更新程序能力说明。缺生产文献、案例正文或原附件时标记相应验证受阻；模拟数据只用于流程测试。不要改原审核、覆盖基线或让候选测试切换线上全局。按05的验收顺序交付实际实现与验证结果。
