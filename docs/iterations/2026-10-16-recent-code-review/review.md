## 1. P2：普通案例追问被当作全库新检索，丢失当前案例范围

位置：`backend/src/agent/routing.py:55`，联动 `backend/src/agent/runtime.py:199–204`。

先问“找一个玉米案例”，再问“这个案例适合什么土壤？”。新增规则把任何包含“案例”、且没有解释关键词的问题归为 `case_reference`；运行时又明确排除这种路由的续问处理。因此第二轮没有传入原案例 ID 和 `case_context_text`，而是重新传整个开放案例库。模型可能换成其他案例回答，原案例关闭后也不能按续问语义报告不可调用。

复现：两个不同案例、模拟模型第一轮只引用其中一个；第二轮捕获模型输入，`previous_user_text` 为空，`available_cases` 却包含两个案例。建议优先识别有明确指代的续问，再区分用户是否主动要求寻找其他案例。

## 2. P2：关闭流程或刷新后无法找回批次回执

位置：`frontend/src/components/literature-batch-import.tsx:157`，关联第 43–67 行。

批次 ID 仅保存在组件 state；重新打开弹窗会清空 ID 和结果，刷新也会丢失。组件只请求 `/imports/{currentId}`，从不查询已实现的 `/imports` 历史列表。因此后台仍在运行的任务、失败原因及逐篇重试入口在关闭弹窗或离开页面后无法恢复。重新上传又会被已有草稿判重，无法继续原流程。

静态数据流确认。建议提供当前账号近期批次入口，或持久化当前批次并在重新进入时恢复查询；不能仅保留后端回执。

## 3. P2：服务中断后的 queued 条目会阻塞界面上的恢复操作

位置：`backend/src/api/literature_batch.py:176–178`；联动 `frontend/src/components/literature-batch-import.tsx:155` 和重试按钮的 `disabled={busy || active}`。

服务在处理超过三篇的批次时重启，尚未取得并发槽的条目永久保持 queued。`with_retry_status` 只允许 warning、failed 或超时 processing 重试，没有区分失去执行者的 queued 条目；前端因此一直判定批次 active，连超时 processing 条目的重试按钮也被禁用。即使保留当前弹窗并等待五分钟，用户也无法恢复任务。

复现确认 queued 的 retryable 永远为 false、超时 processing 为 true。直接手动调用 retry API 能重新调度 queued，但产品界面无法发起该操作。建议在启动时识别中断任务或建立执行租约/恢复状态，并让前端允许恢复整批中断任务。

## 4. P2：自动解析期间的人工标签选择会被后续打标覆盖

位置：`frontend/src/components/literature-workspace.tsx:259–262`，关联第 301、454 行。

上传成功后字段解析先异步执行；此时标签选择器只受 `tagging` 禁用，`extracting` 期间仍可操作。用户手动选择标签后，解析完成调用 `autoTag` 时却使用上传时的 `replacement` 快照（其中 tag_ids 固定为空），而非最新表单。服务端无法保留未收到的人工选择，返回结果又整体替换当前 tag_ids，即使返回空数组也会清空人工标签。

静态数据流确认。建议发起自动打标时使用最新表单选择并保护并发编辑，或在整个自动解析及打标流程期间明确禁用标签编辑。
