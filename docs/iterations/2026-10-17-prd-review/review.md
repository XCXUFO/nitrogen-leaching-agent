## 1. 需要先处理的问题

### R01｜案例容量限制的现状描述不准确

**性质：已核实的基线偏差。影响 M04、能力差异表及 E06。**

位置：[M04 第 3 节](/mnt/e/研究生/毕设/项目相关文档/1017/04_案例与措施管理及检索_PRD.md:19)、[差异表](/mnt/e/研究生/毕设/项目相关文档/1017/12_能力基线与逐项差异.md:30)、[E06](/mnt/e/研究生/毕设/项目相关文档/1017/13_评审决策与验收安排.md:49)。

M04 使用了“不再以固定前 30 条作为候选全集”的描述。实际 [CaseStore.available()](../../../backend/src/storage/case_library.py:193) 会查询全部符合开放条件的记录，再进行去重和容量判断；超过 30 条或材料 JSON 超过 24000 字符时，直接抛出 HTTP 413 / `case_capacity`，不会静默只取前 30 条。显式指定较小案例集合仍可执行。

这意味着问题可能是整个自动案例参考分支不可用，而不只是第 31 条资料漏召回。“先验证是否存在遗漏”不能代替验证容量错误。

建议修改：把基线写为“现有全量材料整体传入模型，超预算会拒绝调用；本轮将候选搜索与材料预算分开”。验收至少区分：31 条去重后独立案例、少于 30 条但字符超限、显式指定案例，以及相关资料处于不同排序位置。预算不足时继续明确提示，不能截断事实或要求关闭真实资料来满足预算。

验证：已有容量测试通过；另外在独立内存库建立 31 条不同正文的开放案例，未指定对象时返回 413，指定其中 1 条时正常取回。

### R02｜断线恢复与主运行统计缺少共同的请求生命周期契约

**性质：实施前契约缺口。影响 M01、M06、M09、M11。**

位置：[M06 事件字段与恢复](/mnt/e/研究生/毕设/项目相关文档/1017/06_路由与Skill编排_PRD.md:72)、[M09 第 6 节](/mnt/e/研究生/毕设/项目相关文档/1017/09_前台执行进度展示_PRD.md:66)、[M11 主运行口径](/mnt/e/研究生/毕设/项目相关文档/1017/11_效果大盘与迭代验证_PRD.md:32)。

文档要求恢复时不重新执行、重跑产生新运行、同一轮取首次主运行，但尚未定义“首次提交响应丢失”时，客户端如何找回该运行，以及网络重发和用户主动重跑如何区分。

当前 [ChatRequest](../../../backend/src/api/chat_schema.py:26) 没有稳定轮次 ID 或幂等请求标识；[运行时](../../../backend/src/agent/runtime.py:120) 每次执行新建 run ID，到执行结束才附给结果，并在 `finally` 中保存 Trace。[RunStore](../../../backend/src/storage/run_store.py:61) 保存最终 Trace，尚无运行创建和逐事件持久化接口。Trace 也没有完整 `ChatResponse` 快照；引用题录还会在 [HTTP 返回阶段](../../../backend/src/api/chat.py:102) 补充。

因此只给已有 Trace 加事件字段，仍不足以保证“任务已成功但响应丢失后恢复完整答案”。这属于新增链路必须补的工作，不是要求重建运行时。

建议增加一份共同契约，具体字段名可在实现时决定：

- 用户提问轮次、一次提交、一次运行分别有稳定关联；网络重发复用同一次提交，主动重新执行创建新运行并关联原轮次和原运行。
- 提交被接受后即可定位运行；恢复查询不会触发执行。相同幂等标识搭配不同输入时明确拒绝。
- 运行开始、事件序号、终态及完整对客结果可恢复；说明终态与结果保存的提交顺序，以及保存失败时如何避免重复调用。
- 断线是否继续执行、进程重启后哪些记录为未知或中断、事件保留期届满如何展示，均有明确规则。
- 恢复接口按现有登录用户或访客归属授权，并只返回对客字段。现有运行详情是开发者接口，不能直接作为公众恢复接口。

新增验收：提交已经受理但首个响应丢失、最终答案完成但客户端未收到、网络重发、用户主动重跑、跨访客读取拒绝。原有断线／乱序／重复事件用例继续保留。

### R03｜正式会话审查与大盘所需数据不能直接由现有评测评分映射得到

**性质：已核实的基线差异及跨模块字段缺口。影响 M10、M11。**

位置：[M10 第 5 节](/mnt/e/研究生/毕设/项目相关文档/1017/10_后台会话审查_PRD.md:74)、[M10 审查更正](/mnt/e/研究生/毕设/项目相关文档/1017/10_后台会话审查_PRD.md:111)、[M11 人工指标](/mnt/e/研究生/毕设/项目相关文档/1017/11_效果大盘与迭代验证_PRD.md:60)。

现有 [EvaluationStore.review()](../../../backend/src/evaluation/store.py:184) 绑定评测 execution，从其 events 取得 run IDs，并要求执行者为本人。已提交评分不能覆盖。其他评审／签核能力也以用例或执行为关联入口。这不是直接对任意正式 Run 保存结构化审查的接口。

现有 [ReviewInput](../../../backend/src/evaluation/contracts.py:183) 的路由结论仅 `yes/no/n.a.`，不支持文档要求的“部分正确／无法判断”独立状态；也没有独立的问题理解、证据相关性和证据充分性结论。M10 表格把检索有效性与充分性放在一行，M11 却要求分别计算两个指标；只记一条泛化结论或备注，无法稳定计算两个分母。

建议明确为本轮需要补的适配层：

- 正式 Run 可直接进入审查，不要求为每条公众问题伪建评测 execution。
- 每个判断维度独立记录适用性、是否可判断、结论和依据；相关性与充分性分别保存。
- 审查修订保留历史和并发版本，每个统计目标只有一份当前有效结论；冲突待复核不进入对应正确率分母。
- 评测旧数据继续兼容；旧 `n.a.` 不能反推成明确的“不适用”或“无法判断”，未采集内容按未知处理。
- 来源、抽样方式、人工／AI 辅助审查身份有可查询标识；自动检查不得补成专业人工结论。

只扩展现有数据模型与入口即可，不需要重建评测平台。上述字段具备之前，可以展示计数，但不应发布依赖它们的正确率或充分率。

### R04｜“明确条件严格筛选”与“未打标资料可召回”之间缺少判定规则

**性质：需求存在实现歧义，尚不是已证实的线上故障。影响 M03、M04、M05。**

位置：[M03 检索规则](/mnt/e/研究生/毕设/项目相关文档/1017/03_文献管理与RAG衔接_PRD.md:55)、[M04 候选规则](/mnt/e/研究生/毕设/项目相关文档/1017/04_案例与措施管理及检索_PRD.md:23)、[M05 条件规则](/mnt/e/研究生/毕设/项目相关文档/1017/05_共享标签与语义映射_PRD.md:34)。

例：用户明确要求“玉米案例”，一条案例正文明确写玉米，但没有作物标签。若先把用户条件转为标签 ID 的硬过滤，这条记录会在正文召回前被排除；即使后面有无标签检索路径，也已经无法兑现该路径。

建议区分“用户对资料适用性的硬条件”和“数据库已有标签”：没有标签属于条件未知，不等同于条件不满足。允许通过正文候选路径核对；已确认冲突的资料排除；资料无法证明符合条件时如实标明，不能包装成严格匹配。推断标签只作辅助，访问权限和停用／删除规则始终严格执行。

补三个联合验收：无标签但正文满足条件；标签与正文冲突；正文与标签都无法确认条件。每种情况记录实际过滤阶段和原因。

### R05｜步骤终态尚未形成可供前台与指标共用的计数表

**性质：统计口径仍需收敛。影响 M06、M09、M11。**

位置：[M06 第 7 节](/mnt/e/研究生/毕设/项目相关文档/1017/06_路由与Skill编排_PRD.md:85)、[M11 工具指标](/mnt/e/研究生/毕设/项目相关文档/1017/11_效果大盘与迭代验证_PRD.md:46)。

M06 将“跳过”列为步骤终态；M11 的工具成功率分母写“已终止且非取消的工具步骤”，按字面可能把从未调用的跳过步骤算进去。M06 同时描述 Skill、内部工具和检索父子步骤，尚未明确汇总时统计哪一层；一个 Skill 与它的内部检索可能重复计数。合法检索空结果属于执行正常还是执行失败，也应与命中结果分开保存和计算。

此外，现有 `outcome=clarification` 需要映射：提出必要澄清可以是正常结束的一次运行，但不应让前台误称原业务任务已完成，也不应在统计中被当成工具失败。

建议在 M06 定义共同状态和统计矩阵，M09、M11 直接引用：

- 执行状态与业务结果分开；合法空结果可正常执行，但不是检索命中。
- 只统计实际开始的目标工具步骤；待执行、跳过不进工具成功率分母，取消和历史未知单列。
- 固定工具与 Skill 的统计层级；父容器不重复计入子工具统计。
- 步骤级取最终尝试状态，尝试级保留每次失败；澄清、局部完成、取消分别定义展示文案和适用分母。

用一组包含“首次失败后成功、正常空结果、计划后跳过、取消、必要澄清”的数据，手算并核对前后台与大盘结果。
