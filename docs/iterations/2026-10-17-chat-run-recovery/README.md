# 聊天运行恢复与真实步骤进度

日期：2026-10-17。承接 V0.3 共享契约，实现 M06 的可恢复提交基础和 M09 的步骤展示增量。前台仍使用现有聊天入口 `/`，旧客户端继续使用同步 `POST /api/chat`。

## 本轮交付

- `conversation/session`、`turn_id`、`request_id`、`run_id` 分离。同一提交重送返回原回执；输入冲突返回 409。显式重新执行保持原轮次、输入和 `primary_run_id`，生成新提交／新运行并关联原运行。第一个成功受理的运行始终为主运行，即使它最终失败。
- SQLite 事务先受理、再创建独立后台任务。唯一约束应对重复／并发提交，响应中断不取消已受理任务。进程重启将未确认任务标为 interrupted，不自动重放工具或模型调用。
- 单调序号事件包含受理、计划、实际 Skill 开始／结束、运行结束。当前仅采集真实 Skill 边界，不声称已有底层工具、内部重试或 Token 流。执行状态与业务结果分开，正常空命中是 no_result，需要澄清是 clarification。
- 完整 ChatResponse（含补齐后的引用元数据、文件证据、warnings、sections、trace_saved）与最终事件／状态同事务写入。事件暂时写入失败时缓存当前执行链的后缀并在结束时补存；后续步骤开始记录受阻时停止调用。最终保存失败不重新执行，明确返回 unknown、result_saved=false；当前进程内仍可提供已算出的结果，页面常驻提示尚未保存。
- 恢复读取只允许原账号或服务器签名访客身份。浏览器先通过握手持有 HttpOnly Cookie，避免首个 POST 回执丢失后丢失归属。跨访客、跨账号和伪造 Cookie 不能读取运行；无公开 Trace 查询。
- 前端按序号合并事件，显示真实能力名称和完成情况；断网先查原提交，不以新标识自动重跑。失败后的主动重试及完成后的重新回答创建关联新运行。新回答仍原位替换展示，后台原运行和主运行关联保持不变。
- 公开体验的并发名额随后台任务保留至结束。已受理提交的重复回执和恢复 GET 不重复消耗执行预算；重复 POST 仍受频率限制。

## 协议

| 入口 | 行为 |
| --- | --- |
| `GET /api/chat/session` | 初始化签名归属，返回 `protocol=chat-runs-v1` 和恢复窗口秒数 |
| `POST /api/chat`，带 `session_id + turn_id + request_id` | 202，返回 owned run envelope；同一提交重复返回原运行 |
| `GET /api/chat/requests/{request_id}?session_id=...` | 按本次提交找回受理回执，首次响应丢失也可查询 |
| `GET /api/chat/runs/{run_id}?after=N` | 原运行状态、完整结果及 N 之后的新事件；不执行模型 |
| 不带轮次／提交标识的 `POST /api/chat` | 保持原 200 同步 ChatResponse；不具备新增幂等保证 |

回执包含 `primary_run_id`、`rerun_of_run_id`、`config_version`、`source=formal`、`mode=auto/specified`。客户端自报 operator_id 不授予归属。恢复接口统一禁止缓存。文件内容不进入公开步骤事件，内部异常不透传前台。

## 部署与保留

复用 `AGENT_TRACE_DB`；新增的提交、身份、事件表自动初始化，已有 Trace 继续可读。仅支持 **单个后端 worker**，与当前本地／公开体验部署方式一致。多进程任务协调不在本轮实现。

`CHAT_RUN_RETENTION_SECONDS` 默认 86400，范围 600—604800；从对话首次受理起固定恢复窗口，之后同对话不滑动续期。过期返回 410，必须新建对话，旧标识保留 tombstone 防止清理后误重做。过期结果／事件在读取时清理，本轮没有全库后台保留清理任务。账号与访客 Cookie 持久化密钥均保存在服务器 SQLite；保留数据库才能在重启后继续识别原归属。

`CHAT_RUN_MAX_ACTIVE` 默认 32，范围 1—256；公开体验沿用其更小的 `PUBLIC_MAX_CONCURRENT`。关闭页面不会主动释放进行中任务所需附件，未续期文件仍按原文件租期清理。
