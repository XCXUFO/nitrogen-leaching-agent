# V1.0 补齐与代码复查

范围：本轮案例与措施库的存储、管理接口、两个 Skill、聊天路由、工作台交互和相关回归。工作区包含其他未提交迭代，本报告不把这些内容视作本轮新增，也不代表全仓库审计。

## 已修复发现

| 优先级 | 触发与影响 | 修复与证据 |
| --- | --- | --- |
| P1 | 先引用 A，再说“再解释这个 B”：历史 ID 可能覆盖当前指定的 ID，导致解释错误案例。只从客户端历史取 ID 也无法可靠支持历史截断后的追问。 | 当前 ID 优先；成功请求后仅保存案例 ID 和用户上下文；每次重新校验开放状态。测试覆盖 A→B、无客户端历史追问、删除后拒用及失败请求不切换对象。见 `runtime.py` 的案例分支。 |
| P2 | ID 直接连接中文（如“C-…的措施”）不匹配 Unicode 单词边界；API ID 大小写与格式不统一。 | 统一 `case_ids.py` 解析与校验，支持中文相邻和小写输入，拒绝不完整或过长 ID。 |
| P2 | 模型因条件不足返回具体追问且未引用案例时，被后处理替换成“没有找到案例”。 | 输出契约区分 complete 与 clarification；保留追问，补充条件后继续原 Skill，连续补充的作物、灌溉条件不会丢失。 |
| P2 | 文本解释后的“再详细解释它”没有原文；“其他案例”还可能因包含“它”误转解释。 | 有界保留用户原文，明确新文本重置上下文；参考意图不被追问逻辑覆盖。新增测试核对实际发给模型的材料。 |
| P2 | 自然语言中写入 31 个案例 ID，可能在内部输入校验处变成通用 500。 | 在 Skill 调用前返回明确 413/case_capacity；实际 `/api/chat` HTTP 测试验证。 |
| P2 | 编辑冲突只有查看提示，恢复操作不完整；任意 409（包括会话繁忙）会误显示案例冲突。 | 按 case_conflict 错误码处理；确认后加载最新内容和 revision，取消时保留输入。浏览器验证冲突→取消加载→确认加载→重新编辑保存。 |
| P2 | 验证面板未指定会话，可能与同一账号普通聊天使用默认会话。 | 面板使用独立且可复用的会话 ID，并兼容没有 randomUUID 的环境。 |
| P2 | 现有构建指纹未覆盖新增案例读取代码，读取规则变动时指纹可能不反映。 | 将案例存储和管理接口加入现有 agent_code_sha256 输入。没有新增版本管理平台。 |

## 复查结论与边界

复查了 SQL 参数化、登录复用、三个管理角色的操作范围、逻辑删除、并发修改检查、无同步缓存时的关闭生效、AI 初稿不自动写库、非法引用拒绝、前端失败保留输入以及案例与文档问答的路由隔离。在本轮覆盖范围内，没有发现尚未修复的阻塞性实现问题。

自然语言路由仍是本项目现有的保守规则方式；模型输出的事实忠实度、场景相关性和通俗程度不能仅凭工程测试证明，需要专业同事用真实材料进行人工验收。初期有界读取的 30 条／24000 字符限制仍然存在，超限明确提示。本次不部署、不填充正式案例数据。
