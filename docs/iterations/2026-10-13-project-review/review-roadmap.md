# 项目评审与后续优化建议

评审日期：2026-10-13。对象为当前工作区，包含 V2.1 页面内历史对话及已有未提交改动。本轮仅新增评审文档，没有修改业务代码、部署或操作正式数据库。

## 判断

项目已具备文献问答、确定性表格计算、文件证据、会话内追问、评测工作台与文献管理的基础。下一阶段建议依次投入：稳定性与发布门禁、会话恢复、文献管理到检索的闭环、专业质量评测。

当前优先事项是解决已经确认的问题，并使它们能被持续集成拦截。暂不需要以大规模架构重写作为前提。

## 产品优化方向

### 1. 会话恢复与可控记忆

V2.1 已完成同一聊天页面的 10 个对话切换，这是一期约定范围。当前状态在 `useConversations()` 内，离开聊天页、刷新及身份切换都会清空。附件为后端 FileStore 内存数据，闲置租约 24 小时；TaskState 为独立的 30 分钟内存租约。窗口心跳续的是附件，不是完整服务端任务状态。部分指标可从最近用户历史恢复，但这不等于任意时长或服务重启后都能续聊。

建议分步实施：

1. 先支持当前标签页内跨页面导航及刷新恢复。需要同时设计附件失效提示与重传，不能仅把 file_id 写入 sessionStorage 后宣称附件已持久化。
2. 再建立按身份归属的 conversations/messages/attachments 数据模型，支持列表、打开、删除及登录后恢复；游客与账号的归属转换应显式定义。已有 RunStore 用于运行审计，不能直接视为已经具备用户可恢复对话服务。
3. 将短期消息和明确任务条件分开存储，保留作物、目标指标、选中文件、时间范围及来源。前端当前仅发送最近 12 条消息、每条 4000 字，长会话不能只依赖继续截断原文。需要摘要时保留来源轮次、可更正性和原始消息，不让摘要替代计算证据。
4. 给保留对话增加可删除入口，并补充每个身份的附件总量/字节预算。当前 10 个对话各可带 10 个附件，而后端文件数和 128 MiB 内容预算为全进程共享，历史保留后应重新评估容量。

验收重点：切页/刷新恢复、身份隔离、长对话条件不串、后端重启后的明确恢复策略、旧文件失效与重传、删除后资源释放。是否需要关闭窗口后保留由下一期产品范围确定，本轮不擅自扩大一期承诺。

### 2. 文献管理到问答的发布闭环

当前文献管理数据库负责登记、标签和停用；检索索引仍由 `backend/scripts/index_papers.py` 建立，原文展示仍使用 `backend/src/rag/documents.py:13` 的静态 catalog。文献的“登记/启用”并不自动意味着“已进入问答知识库”，停用记录也不会直接撤回既有 Chroma 片段。这是代码链路的观察，不将尚未承诺的自动索引能力当作既有功能回归。

建议增加独立的“发布到知识库”状态：待处理、索引中、可检索、失败、已撤回；统一文献 ID、版本、片段、原文入口及引用元数据。支持失败重试、增量更新和旧版索引回滚。登记和发布可以分离，界面应明确当前可用范围。

验收重点：发布一篇文献后可检索并正确引用；撤回后新回答不再召回；更新后引用版本可追踪；索引失败不会被显示为可检索。

### 3. 用专业评测决定回答质量优化

确定性计算及单元格证据、引用定位、Run trace 和评测工作台是可继续利用的基础。仓库专业审核记录仍有待审项，不能把 mock 测试和既有调优集的通过率当作专业正确率。

建议冻结一批未用于调优的真实问题，覆盖普通问答、文件计算、长文档、多文件、多轮条件、材料不足及冲突证据；由业务人员审核切题性、数值/单位、引用支持和适用范围。指标至少区分任务成功率、引用支持率、不当外推、P50/P95 延迟和单轮调用成本。

当前会话文档每次提问都会重新分块，并用词语命中数排序（`backend/src/agent/session_context.py:19`）。可先测长文档召回与耗时，优先缓存分块并明确目标文档，再决定是否引入语义检索或 reranker；不预设更复杂的模型一定更好。

### 4. 发布与代码维护

本轮状态检查见 48 个已跟踪修改、101 个未跟踪条目，其中含目录。这是工作区条目统计，不是本轮修改数。当前可运行工作区不等于可由单个 Git commit 重现的交付物。建议整理完整源码、锁文件、数据/索引版本和构建 manifest，再做发布与回滚演练。

README 和开发指南仍包含旧阶段、30 分钟/32 文件等历史描述，与当前 24 小时/256 文件和 V2.1 能力不一致，应同步当前能力矩阵与运行约束。

实现下一期功能时顺带拆分复杂模块：`runtime.py` 的路由/附件选择/任务执行，`literature.py` 的路由/存储/业务校验，以及文献前端的表单/请求状态。按已验证行为逐步拆分，避免单独开启大范围重写。

## 建议实施顺序

| 批次 | 目标 | 完成判据 |
| --- | --- | --- |
| 第一批：稳定性补丁 | 超时、就绪、代理边界、依赖、文件名及 API 契约；修复并纳入回归 | 本轮缺陷转成期望行为测试；CI 自动运行核心浏览器流程；真实入口慢请求与启动验证通过 |
| 第二批：会话连续性 | 跨页面/刷新恢复，统一会话与附件生命周期，身份隔离 | 原消息与条件可恢复；附件可用性真实；容量及删除释放可验证 |
| 第三批：文献发布与质量 | 文献登记到索引/引用闭环，独立专业评测 | 新增和撤回可验证；引用可追溯；给出独立任务成功率及质量问题分类 |

专业评测准备可与前两批并行推进。流式输出、回答停止和请求状态反馈可在超时/幂等问题处理后进入体验优化；完整多 worker 扩容需先解决共享会话和文件状态。
