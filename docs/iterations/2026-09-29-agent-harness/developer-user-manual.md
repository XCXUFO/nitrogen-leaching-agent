## 1. 平台的目的、意义和当前定位

前台农业模型助手面向提问者，提供文献问答、已有模型结果表的确定性计算、有限组合回答和缺项澄清。测评工作台服务于它的研发与交付：固定测试条件，留下可核对的事实，组织功能评价与专业审核，再验证改动是否有效。

产业落地时，团队需要回答的不只是“这次演示有没有输出”，还包括：

| 管理问题 | 当前承载方式 |
|---|---|
| 这一版交付覆盖哪些能力和标准？ | 版本化 Case、冻结 Task、实际构建/运行配置 |
| 谁测了哪一条，过程和结论在哪里？ | Execution、Event、Review、身份和时间 |
| 某个答案的数值或专业断言来自哪里？ | Run Trace、文件证据、文献片段、材料指纹 |
| 哪些失败已有人处理，修复依据是什么？ | Issue 状态、负责人、处理历史、新执行复测 |
| 换代码/知识库之后旧能力退化了吗？ | 冻结回归基线、新版本重跑、逐轮比较和新评分 |
| 结论是程序检查、AI 辅助还是专家判断？ | 三类独立记录及各自权限 |

平台的价值是让“测试—解释—改进—验证”有连续证据。它不会根据评分自动训练或修复 Agent，不会把 HTTP 200 自动换成正确答案，也不自动决定正式发布。

目前已从基础面板拆成分组侧栏和独立模块页面，具备 Task → 执行 → Run → 评分 → Issue → 复测基础闭环。完整产业中后台仍在建设，资产生命周期、任务人员管理、持久化调度、企业身份体系等边界见第 17 节。

## 2. 架构：前台、工作台、Agent 怎样连起来

### 2.1 系统结构

```text
浏览器：Next.js / React 前端
  ├─ /                         前台聊天、附件、答案与引用
  │     ├─ POST /api/files      上传临时问答附件
  │     └─ POST /api/chat       普通聊天请求
  └─ /evaluation/...           测评工作台与角色导航
        └─ /api/eval/...        带 Bearer 密钥的评测接口
                 │
FastAPI 后端     │
  ├─ EvaluationService：执行所有权、版本检查、事件、评分、流程
  │     └─ query 复用同一个 chat 处理函数
  ├─ Agent Runtime：规则路由、会话状态、有限步骤、证据与 Trace
  │     ├─ 文件路径：表格检查 → 确定性分析 → 文件证据
  │     ├─ 知识路径：检索 → 文献回答 → 引文与片段
  │     ├─ 组合路径：文件事实 + 有引用的可能机制 + 局限
  │     └─ 直接回答 / 澄清 / 范围外响应
  ├─ SQLite：Run、Case、Task、执行、评分、问题、审核、回归记录
  ├─ 文件系统：原始资产、资料、索引、本地模型、备份
  └─ 单进程内存：临时附件、对话上下文、当前自动重跑任务
```

前端是操作界面，后端负责权限、状态、执行和存储。实际访问地址默认是前端 3000、后端 8000，前端通过 `NEXT_PUBLIC_API_BASE_URL` 指向后端，默认 `http://localhost:8000`。该公开前端配置在构建时确定；换远程地址时应同步配置并重新构建。

文献问答仍依赖检索资源及外部模型服务。离线加载本地嵌入模型不等于系统所有能力离线。文件极值是程序读取已有输出表，不是调用 WHCNS 再做一次仿真。

### 2.2 一次后台提问的真实链路

1. 浏览器发送 `POST /api/eval/executions/{eid}/query`，附身份密钥和问题。
2. 后端检查身份、执行所有者、执行是否开放、是否忙碌，以及关联 Task 的配置是否与当前运行一致。
3. 服务器从执行上下文取会话、历史和附件，构造普通 `ChatRequest`；浏览器不能任意指定另一个会话或把外部 Run 硬塞进此执行。
4. 复用聊天入口和 Agent Runtime，调用文件或知识能力。
5. Runtime 记录本轮 Run/Trace；评测层将回答或错误连同 Run ID 追加为执行事件。
6. 浏览器显示本轮结果。执行者完成判断后单独提交评分，后台冻结评分与执行。

它验证的是前台也使用的 Agent 能力，但并未操作前台的输入框、滚动条和多文件选择器。前台体验仍需真实浏览器验收。

### 2.3 前台数据如何与后台对应

| 来源 | 有 Run 吗 | 自动有 Execution/Review 吗 | 如何追踪 |
|---|---|---|---|
| 前台一轮问答 | 正常持久化成功时有；失败按实际记录确认 | 没有 | 开发者在运行记录查时间、问题和 Run ID |
| 后台一次提问 | 成功持久化时关联同一轮 Run；缺失会标记 | 已属于 Execution，评分需另提交 | 执行详情 → 本轮 → 查看 Trace |
| 上传、清除、移除、手动备注 | 本身不是问答 Run | 后台可有对应 Event | 执行事件或人工验收文档 |
| 自动回归重跑 | 每个实际提问生成新 Run | 生成新 Execution；不自动评分 | 回归对比 → 打开新执行 / 人工评分 |

前台 Run 不是自动收件的待评分任务。当前没有“一键把任意前台历史会话导入 Execution”的功能。前台发生故障时，先保留原 Run 和人工记录，再按需要创建 Case 和新的复现执行；这两次运行必须分别标识。

## 3. 数据对象和版本关系

```text
资产（原件、路径、指纹、来源） → Case 的附件与核验依据
Case@版本 → Task 固定多个 Case 版本、构建和运行配置
                  └─ Execution（某人对一个 Case 版本的一次测试）
                       ├─ Event：上传/重置/提问/手动动作等
                       │    └─ 提问 Event → Run → Trace/答案/证据
                       ├─ Review：一次冻结开发试评
                       ├─ Assessment：独立 AI 或专家审核记录
                       ├─ Issue：失败轮次和原评分 → 新执行的复测关联
                       └─ Regression：冻结快照 → Replay → 新 Execution
```

| 对象 | 保存什么 | 版本或变更规则 |
|---|---|---|
| Case | 编号、版本、步骤、前提、标准和附件要求 | 发布后不能覆盖；改标准应发更高版本 |
| Case Draft | 未发布内容、关联资产、修订备注 | 保存生成新修订，发布校验打开的修订号 |
| Task | 1–50 个 Case 版本、构建标签、知识库标签、运行配置清单 | 当前用于冻结批次；不是完整排程或任务审批系统 |
| Execution | Case 版本、测试者、可选 Task、操作序列 | 同一用例可执行多次；评分后冻结 |
| Review | 总体、四维评分、备注、事件/Run、Case 快照 | 每个执行最多一份，类型为 `development_trial` |
| Assessment | 类型、结论、材料路径/指纹、依据、审核身份、可选执行关联 | 追加保存，不覆盖 Review 或历史审核 |
| Issue | 原执行、原问题/答案/错误、Run、Review、负责人、状态、历史 | 并发修订保护；复测保留新旧证据 |
| Regression / Replay | 基线快照及每次重跑进度、候选执行 | 基线不被新结果覆盖；完成不等于通过 |

必须区分三种“版本”：

- **Case 版本**：测试标准变了没有，例如 F05 v2 与 v3。修复代码后验证原缺陷，优先保留相同 Case 版本。
- **构建版本**：哪份源码交付在运行，当前快照使用 `delivery-20261004-ee879b36e1ab`。
- **运行配置版本**：构建加启动配置/指纹摘要。交付时记录为 `delivery-20261004-ee879b36e1ab:0ef05c12b9e1ace7`，实际测试前仍应查 `/api/eval/config`。

Task 的 `knowledge_version` 是开发者填写的可读标签，不会自动重建或切换知识库。服务器另存实际知识配置和启动清单。已发布 Case、旧执行和旧评分不会因为你发新版本而自动迁移。

## 4. 身份、权限与多人分工

### 4.1 权限表

| 能力 | tester | developer | reviewer |
|---|---|---|---|
| 查看 Case 与任务 | 可以 | 可以 | 可以 |
| 创建自己的执行、准备自己的任务执行、提交自身试评 | 可以 | 可以 | 可以 |
| 阅读执行 | 自己的 | 全部 | 全部 |
| 改动/评分他人的开放执行 | 不可以 | 不可以 | 不可以 |
| 创建 Task、编辑/发布 Case、上传/登记资产 | 不可以 | 可以 | 不可以 |
| 查看资产、核实候选输入输出配对 | 不可以 | 查看并登记候选 | 查看并提交核实 |
| 审核队列 | 不可见 | 查看、分派专家 | 查看、专家审核、记录分歧处理 |
| 保存 AI 辅助复核 | 不可以 | 可以 | 不可以 |
| 保存领域专家审核 | 不可以 | 不可以 | 可以 |
| Issue、回归、Run Trace、统计、任务证据导出 | 不可以 | 可以 | 不可以 |

角色菜单只是界面表现，后端仍独立校验权限。普通评分中的“开发试评”是记录类型，所有执行者提交的普通评分都属于该类型。开发者权限不赋予领域专家身份。

当前是静态密钥绑定身份，没有组织/租户隔离、网页登录注册或自助找回。任务准备不等于给其他人分派测试任务；审核队列的分派则是已实现的专家分派。分派也不是严格的“只有分派专家才能看到该执行”的数据隔离机制。

### 4.2 推荐分工

开发者维护标准和环境、组织任务、分析 Trace、登记问题并修复；测试者用自己的身份执行和评分；专家以 reviewer 身份判断专业材料与断言；负责人汇总并决定交付范围。

当前所谓“独立复测评分”指新执行上的新评分，没有强制要求评分人必须与初测或修复者不同。需要人员独立性时，由团队制度安排不同真实人员，并在审核/验收记录中体现。禁止用一个共享身份伪装多人独立评测。

## 5. 工作台总览与导航

本机工作台入口 `http://localhost:3000/evaluation`。登录后菜单分为“评测管理”“质量管理”“资料与证据”，支持收起、窄屏抽屉、当前项高亮和面包屑。详情有独立 URL，可以分享给有权限的人。

| 菜单 | 地址路径 | 主要目的 |
|---|---|---|
| 工作台总览 | `/evaluation` 或 `/evaluation/overview` | 汇总入口、执行及评分分布 |
| 任务管理 | `/evaluation/tasks` | 创建批次、准备执行、查看进度/看板、导出证据 |
| 用例库 | `/evaluation/cases` | 阅读标准、检索版本、管理草稿 |
| 执行记录 | `/evaluation/executions` | 实际测试、查看历史、提交评分 |
| 回归对比 | `/evaluation/regressions` | 保存基线、重跑、逐轮比较 |
| 审核队列 | `/evaluation/reviews` | 分派专家、查独立审核与分歧 |
| 问题管理 | `/evaluation/issues` | 问题负责人、状态、处理历史与复测 |
| 资产目录 | `/evaluation/assets` | 登记原件、文件指纹及输入输出配对 |
| 运行记录 | `/evaluation/runs` | 按会话调查多轮问答及每轮 Agent 运行 |

开发者总览包含开发试评分布；tester 的“近期可见执行”基于当前读取的一页，不能当成全库总数。执行列表默认每页 50 条；会话运行记录默认每页 20 条，可选 10、20、50、100 条。刷新浏览器需重新登录；未提交的局部表单内容不会可靠保留。分享详情 URL 不会分享你的登录权限。

## 6. 资产目录：先让材料可核对

### 6.1 三种“文件”的区别

| 类型 | 用途与生命周期 |
|---|---|
| 前台/执行中的临时附件 | 供当前问答读取，单份不超过 10 MiB；过期/重启可能失效 |
| 资产目录中的资料 | 登记路径、来源、指纹，上传方式会保存原件；可供 Case 附件、配对核查和回归复原 |
| 审核表中的材料路径和 SHA-256 | 引用一份审核依据，当前表单不会自动上传或读取它；负责人需确保材料可访问 |

登记资产不会自动将 PDF 加入 RAG 知识库，也不表示这份材料的内容已获专家认可。

### 6.2 登记已有本地材料

1. 打开“资产目录 → 登记本地资产”。
2. 选择类型，如结果表原件、模型输入、模型输出或证据材料，以页面选项为准。
3. 填项目 `data/` 或 `docs/` 下的相对路径、来源和备注。例如 Nbal 原件路径为 `data/raw/whcns/received-2026-09-26/package/模型/Nbal_out.xls`。
4. 点“登记资产”，确认返回文件名与 SHA-256。路径必须是服务器可读文件，不能直接填写测评者电脑的桌面路径。
5. 用作 Case 固定附件的表格应登记为 `result_fixture`，且为 XLS/XLSX、大小不超过 10 MiB。

### 6.3 上传新材料

1. 先填页面上方的资产类型、来源和备注，上传表单复用这些字段。
2. 在“上传并登记资产”选择文件并点“上传资产”。支持 `.xls/.xlsx/.csv/.json/.txt/.md/.pdf/.docx/.zip`。
3. 普通资产单份上限 40 MiB；结果表原件仍受 10 MiB 限制。
4. 系统保存在 `data/eval/uploads/<随机目录>/`，计算指纹并登记。同名文件不会因此覆盖既有原件。

不要认为备份 SQLite 就备份了这些文件；资产原件需另行归档，见第 15 节。

### 6.4 候选配对与专家核实

开发者选择模型输入和输出，记录依据，保存“候选配对”。实际审核人以 reviewer 登录，选待核实候选、对应输入/输出和 `evidence` 类型资产，填写运行来源依据后保存核实。

核实前程序会重新核对输入、输出、证据文件的指纹；但“材料能否证明实际运行配对”仍由审核人判断。同一个文件夹、同名或聊天中指定作物，都不能自动证明配对。PR01–PR03 缺实际运行来源时继续标缺材料。

## 7. 用例库：把模糊要求写成可执行标准

### 7.1 查看已发布版本

在“用例库”按编号/版本/标题检索，按类别或专业审核状态筛选，点“查看用例”。打开时核对明确版本，例如 `F05@2`。各类别码为 A、K、F、B、X、O、NEW，当前界面直接显示代码；新团队应在自己的用例规范中明确类别含义，不凭字母替代阅读标题、前提和标准。

### 7.2 创建与编辑

两条入口：现有用例详情 → “复制当前用例为新草稿”；或用例库 → “管理草稿” → “新建空白用例”。通用草稿页没有选中现有用例时，复制按钮不可用，从具体用例详情复制即可。

| 字段 | 填写方法 |
|---|---|
| 用例 ID / 版本 | 稳定业务编号；新编号从 1 开始，既有编号更新须高于已发布最高版本 |
| 标题 | 说明要验证的能力或故障，例如“移除结果表后追问必须要求重新上传” |
| 类别 / 优先级 | 选现有类别与 P0/P1/P2，团队先统一使用尺度 |
| 来源 | 需求、真实问题单、人工发现或资料来源 |
| 前提 | 当前附件/会话状态、所需材料、适用范围 |
| 附件要求 | 每行一个文件名，并勾选相应结果表资产 |
| 预期标准 | 每行一个可判断的结果，不用“回答合理”代替具体标准 |
| 步骤 | 动作、说明、原问题、附件名；顺序应能由另一人照做 |

步骤动作有 `query`、`upload`、`remove_attachment`、`clear`、`refresh`、`wait`、`manual`。这些是测试说明；保存用例不执行它们。后台自动回归也只支持其中可复原的实际事件。

例如：“查询最大值应给约 3.6593、模型日序 283、C284/A284；有效附件下追问最小值应给 0、首次日序 2、191 条并列；不能自行推断公历日期。”这些标准比“能回答氮淋失问题”更易核对。

### 7.3 保存、并发和发布

1. 填表并关联结果表资产，点“创建草稿”。
2. 后续修改点“保存新修订”，可以“查看修订历史”。
3. 保存后确认无未保存改动，再点“发布冻结版本”。
4. 发布前检查材料指纹和版本递增；发布成功后在列表核对新版本。旧版本和已有评分保持不变。

页面带有未保存改动时不能发布。其他人保存了新修订，旧页面发布会因 `expected_revision` 冲突被拒绝。先保留自己的未保存文字，再决定是否点“重新打开已保存修订（丢弃本地修改）”，核对差异后继续。普通刷新目录不会替你合并多人编辑。

### 7.4 批量导入

展开“批量导入草稿”，粘贴 1–50 个用例的 JSON 数组或包含 `drafts` 数组的对象。可以是 Case 对象，或包含 `case`、`fixture_asset_ids` 的草稿对象。整批校验通过才保存，导入不自动发布、执行或评分。

以下是无附件的结构示例，编号是示例，不要直接当正式测评结果导入：

```json
[
  {
    "case_id": "DEMO_CAPABILITY",
    "version": 1,
```

## 8. 任务管理：组织一轮可比较的评测

1. 确定本轮目的、参与者、资料、Case 版本和运行构建。不要在测试进行中悄悄换构建。
2. “任务管理 → 新建任务”，填写任务标题；构建版本会从服务器读取，须与真实运行构建一致。
3. 填知识库版本标签，注明对应资料/索引批次。例如团队可采用有归档依据的日期或批次名；标签本身不证明内容相同。
4. 检索并勾选 1–50 个已发布 Case 版本，点“创建任务”。
5. 将任务链接、测评者说明书、指定附件及唯一验收文档分发给测试者。任务模块暂不替你完成人员分派或消息通知。
6. 各人登录自己的身份，进入任务点“批量准备我的执行”，逐项执行并评分。
7. 开发者在详情查看整体进度和“冻结任务看板”，需要最新数据时点刷新。

批量准备是幂等补齐个人缺少的执行，**不是批量自动跑题**。任务进度按用例版本覆盖情况计数；看板按执行计数，同一 Case 多次复测可能占多条，两个数字回答的问题不同。

关联 Task 的执行在创建、提问、上传、重置、移除附件时校验冻结配置。配置变了，旧任务保留查看、已保存证据的评价和手动说明能力，新版本应新建 Task/Execution。不能通过手改构建标签绕过检查。

详情中的“下载任务证据 JSON”导出冻结任务、Case、执行、Run、评分、Issue/复测和审核等关联材料并附指纹。它用于审阅与留档，不是数据库恢复备份；应按项目资料权限保存。

## 9. 执行记录、评分与统计

执行者可从任务打开已有执行，或“执行记录 → 新建执行”选择 Case 和可选 Task。具体上传、提问、手动记录和评分步骤见测评者说明书。开发者可阅读所有执行，但只能操作和评分自己的开放执行；要分析别人失败，直接读原记录和 Trace 即可。

四维评分为路由、工具、证据、答案。总体为通过、部分通过、不通过、受阻；证据和答案允许“部分”，路由和工具不提供该选项。受阻要求四层全为 `n.a.` 且有原因；通过不能带 `no/partial`；部分/不通过要有具体说明。

评分需至少有提问或上传，纯手动备注不能正常提交非受阻评分。Trace 缺失或任务运行版本不一致时不能把执行记成有效通过。评分保存时同时冻结 Case 快照、事件序号、Run ID 和实际 Run 配置版本，评分后不可继续修改执行。

### 统计怎么读

- 待评分不算通过；受阻单列。
- 四层统计剔除本层 `n.a.` 和受阻样本，分别展示是、部分、否。
- 任务看板“有效评分分母”只含总体通过、部分、不通过；每个执行计一次。
- AI 辅助与专家审核记录单列计数，不混成专业准确率。
- “严重回归”只在基线和候选均已提交开发试评时，标记通过→不通过或证据/答案是→否，仍需人工解释。

举例：10 次执行中 4 通过、2 部分、1 不通过、1 受阻、2 待评分，当前有效评分分母为 7，不能写“8 次测试全部完成”或把 4/10 当作可比较的模型专业准确率。跨版本比较还需保证 Case 版本、评分人群和样本构成可比。

## 10. 运行记录：把失败定位到具体环节

### 10.1 打开正确的 Run

优先从执行详情失败轮次点“查看 Trace”，会打开所属会话。前台故障可在“运行记录”按会话 ID/主题、时间、状态、累计耗时和操作人查询，再逐轮展开 Trace。无登录的前台操作人是浏览器本地生成的游客 ID，不代表已核实身份；旧 Run 仅保存会话哈希，以该哈希作为旧会话 ID 展示。

一个 Run 只对应一轮提问；会话详情按顺序展示所有已保存的问答和运行前后状态。排查多轮上下文问题应连看前后两轮。前台 Run 不会自动生成 Execution 或评分，需要评分时应新建后台执行并明确这是一次新的运行。

### 10.2 推荐阅读顺序

| 区域/字段 | 检查什么 | 容易误解的地方 |
|---|---|---|
| `config_version`、`config_manifest` | 是否实际运行了待测代码/配置/索引 | 仓库 HEAD 不代表含大量未提交文件的运行版本 |
| 路由 `decision` | 最终路径、reason_code、计划 skills | 计划工具不等于实际调用，最终路径可能因附件问题转澄清 |
| 工具 `tool_calls` | 实际 skill、状态、耗时、错误码 | 工具成功只说明调用完成 |
| 状态 `state_before/after` | 指标、运算、作物、附件摘要有无正确继承 | 附件引用摘要不是文件内容 SHA-256 |
| 证据 `evidence` | 文件位置/单位/范围或文献片段及出处 | 检索到片段不代表支持所有机理断言 |
| 答案关联 `sections` | 文件观察、文献推断和局限是否正确分开 | 简单文件答案可能 `sections=[]`，继续看 evidence |
| `warnings`、`outcome` | 是否只完成部分、需要补材料 | HTTP 200、`status=ok` 可以同时伴随 `outcome=partial` |

路由值包括 `FILE_ANALYSIS`、`KNOWLEDGE`、`COMPOSED`、`CLARIFY`、`DIRECT`、`OUT_OF_SCOPE`。`status` 是程序运行状态，`outcome` 是任务完成程度，Review 才是人的质量判断；这三个维度不能互相替代。

Trace 不保存模型思维链。文件事实定位到 SHA-256、表名、数值单元格/日序单元格、数据范围；文献事实定位到片段和引用。对于“为什么最大值这么高”，即使数值正确，也需独立核查机制引用是否适用于该作物和情景。

### 10.3 示例：追问丢失字段如何调查

假设用户先问 leak_NO3 最大值，再问“那最小值呢？”却收到不合理澄清。这只是排查示例，不代表当前已知故障。

先查第一轮有没有成功运行文件工具、`state_after.current_metric` 是否为 leak_NO3；再查第二轮 `state_before` 是否承接该字段、附件是否仍有效、是否出现 `inherited_metric`。若第一轮已经无有效附件，可能是上传/上下文问题；若指标继承正确但算错，则转查表格字段、单位、运算和单元格。若数值正确却解释过度，则查回答组织与文献证据，不盲目修改计算代码。

## 11. 问题管理：从失败到复测关闭

### 11.1 登记 Issue

前提是有一份**部分通过或不通过**的开发试评，并存在带 Run 的具体提问事件。

1. 打开失败执行，点“登记问题 / 关联复测”。
2. 在“从失败评分登记问题”选择出问题的轮次。
3. 填标题、负责人和证据说明；写清实际结果、预期与原文/Trace 位置。
4. 点“登记问题”，系统绑定原问题、回答/错误快照、Run、Review、Case 版本和 Task。
5. 从“问题管理”打开问题详情，更新状态与处理备注。

负责人目前是文本字段，不是有通知和授权联动的用户分派系统。登记失败也不会自动发消息。

纯 UI 问题、仅上传失败而没有提问 Run、或受阻执行目前不能直接走这种 Issue 创建入口。保留在唯一人工记录中，开发者再补适用 Case/复现证据；不要伪造一个失败 Run 来满足表单。

### 11.2 手动状态流

正常流程为：待处理 → 处理中 → 待复测 → 已关闭。状态更新必须附处理备注，页面会提交当前修订号。多人同时处理遇到冲突，刷新读取新记录后再决定，不能用旧状态覆盖新历史。

允许必要的退回：处理中可回待处理，待复测可回处理中，已关闭可重新进入处理中。直接从待处理跳到关闭会被拒绝。手动关闭仍须最近一次复测通过且实际 Run 版本已核验。

### 11.3 修复后关联复测

1. 保留原 Issue，完成代码/配置修复并形成新的构建记录。
2. 在同一个 Case 版本下创建**新的执行**；构建变化时使用新的 Task，或清楚标记的独立执行。
3. 新执行所有者实际测试，提交新的评分。不能用原执行或只写修复备注代替复测。
4. 从**新执行详情**点“登记问题 / 关联复测”。页面顶部的“关联执行”应是新执行，不是旧失败执行。
5. 在“关联复测结果”选原 Issue，核对自动显示的实际 Run 配置与修复版本，点“保存复测关联”。

**当前程序会随关联结果自动更新 Issue：**通过且版本核验成功 → 已关闭；部分/不通过 → 处理中；受阻 → 待复测。自动关联更新与手动状态流是两条不同操作路径。后续再关联失败，先前已关闭问题会重新进入处理中，历史保留。

修复版本必须等于复测 Run 中保存的构建名或完整配置标识，不能填关联时服务器的任意当前版本。无 Run、缺 Trace、混用版本不能构成有效通过。同一复测 Execution 当前只能关联一次问题复测，不能复用它给多个 Issue 批量结案。

看板的“已解决”依据最近一次通过且版本核验成功的复测；它是证据口径，不应只看手动选择的状态标签。修改标准后发了 Case v3，也不能拿 v3 执行直接关闭 v2 的原 Issue，应保留原标准的复测链并另行说明需求变更。

## 12. 回归对比与独立审核

### 12.1 建立和使用回归基线

1. 打开值得反复验证的执行，先核查事件和证据。建议评分后再保存，便于比较冻结评分。
2. 点“保存基线 / 回归对比”，填写基线标题和备注，点“保存为回归基线”。允许未评分执行，但基线需有 1–20 轮提问。
3. 系统冻结当时的执行、Case、Trace 和已有评分。之后才补的原执行评分不会回填这份快照；需要时另存新基线。
4. 在基线条目点“用当前版本重跑”，等待进度，必要时“取消重跑”。最多同时两项，实际会调用工具和模型服务。
5. 结束后点“比较结果”，选择上下/并排布局，逐轮核对原问句、回答、路由、工具、数值证据、引用、错误、耗时和版本。
6. 点“打开新执行 / 人工评分”，由新执行所有者核查并提交，再回比较页重新点“比较结果”取最新评分。

新执行归发起重跑的身份所有，**不会自动加入旧 Task 或新的候选 Task**。因此重跑能用于基线比较和 Issue 复测，但不要期待它自动进入候选任务的执行分母。若要求测试者亲自独立执行并进入正式任务，应让该测试者在新任务中另建执行；专家也可另做独立审核。

回归重放的是**基线实际发生的事件**，不是自动照着 Case 文本补齐所有步骤。原执行没做的步骤不会因为写在 Case 中就自动完成。

### 12.2 自动重跑的限制

支持提问、重置上下文、移除附件和可复原的成功上传。附件要有冻结 Case 登记的原件路径且 SHA-256 一致，每份不超过 10 MiB，单次重跑附件累计不超过 64 MiB。

人工缩窗、等待检查、页面刷新备注、无法复原的上传失败或缺原件，会在前面的可自动步骤完成后停止并显示受阻步骤。若第一步就受阻，可能没有创建新执行。程序不替你跳过人工动作后评分通过。

当前任务调度在进程内，重启后未完任务标记中断，需要重新发起，已完成 Run 保留；并没有持久化队列和自动断点续跑。文字/引用变化也不自动表示质量提升，需对照同一标准判断。

### 12.3 专业审核队列

开发者打开“审核队列”，筛选或检索目标执行；已有开发试评后，选择真实 reviewer 身份并点“分派审核”。可分派多人，各自保存独立意见。没有 reviewer 可选时，应先合法配置身份，不能借 developer 将 AI 复核写成专家签核。

审核人从“打开执行与审核表单”核对冻结回答和原文，填写结论、材料路径/指纹与依据。developer 在同一入口保存的是 `ai_assisted`，reviewer 保存的是 `domain_expert`。表单只记录所填材料引用，不自动读取文件验证其真实性或专业内容。

| 队列状态 | 含义 |
|---|---|
| 待开发评分 | 执行尚无普通试评 |
| 待分派专家 | 已评分，尚未分派且无专家记录 |
| 待专家审核 | 有待完成的分派或仍无专家记录 |
| 专家结论一致 | 当前专家记录结论值一致，可能一致失败，不含最低人数门槛 |
| 专家结论有分歧 | 当前专家记录出现不同结论 |
| 分歧已记录处理意见 | reviewer 对当前全部专家记录另存了处理意见 |

分歧处理保留全部原审核，结论可以仍待核实。新增专家记录会使原先只覆盖旧记录集合的处理意见失去当前有效性。该流程还不是正式发布审批或专业通过率系统。

## 13. 完整闭环示例：文件追问问题的处理

以下是演示情境，不是对当前产品故障或人工通过的宣告。编号中的 T、E、R、I 仅帮助理解，实际使用服务器生成的 ID。

| 阶段 | 操作者和动作 | 产出与下一步 |
|---|---|---|
| 定义标准 | 开发者检查 F05 v2 及 Nbal 原件指纹 | 明确最大值、最小值、日序和单元格标准 |
| 组织初测 | 开发者在构建 A 下创建任务 T1 | 冻结 F05 v2、实际运行配置和知识库标签 |
| 初测 | 测试者创建 E1，上传，问最大值，再追问最小值 | 上传事件及两轮 R1/R2；假设第二轮未继承字段 |
| 评价 | 测试者核对原件，提交 partial/fail 和依据 | 冻结评分 V1，把 E1/R2 交开发者 |
| 建问题 | 开发者从 E1 选 R2 对应轮次登记 I1 | 原问题、原答、评分、负责人不丢失 |
| 定位修复 | 查两轮状态、路由和附件，再实施有证据支持的修复 | 保存修改和测试结果，Issue 标处理中/待复测 |
| 回归检查 | 将已评分 E1 保存基线，用构建 B 重跑 | 新执行 E2、新 Run；逐轮比较，人工新评分 |
| 独立复测 | 若需独立测试者和任务统计，创建 B 的 T2，由测试者另建 E3 | F05 仍为 v2，原件相同，新评分来自真实执行 |
| 关联结果 | 开发者从选定的新执行关联 I1，核对 B 的实际 Run 版本 | 通过且核验成功自动关闭；失败转处理中；受阻待复测 |
| 专业核查 | 若涉及机理解释，reviewer 对具体执行逐断言查原文 | 独立专业结论，不由文件算对或回归完成代替 |
| 留档 | 导出任务证据，更新唯一共编验收记录，保留备份 | 任何人可从问题回到原回答和修复后的证据 |

原表例子的最大值约 `3.65926384925842 kg N ha-1`，模型日序 283，`Nbal_out!C284/A284`；最小值 0，首次日序 2，`C3/A3`，191 条并列，352 条记录。这只证明该文件的计算预期，不证明其实际输入输出配对，也不证明最大值的真实成因。

整个闭环的完成标准是：标准和材料可追溯、原失败有证据、修复版本可识别、新结果经真实判断、问题处理历史可回查。PR07–PR09 等专业事项缺独立审核时，必须继续单列待办。

## 14. 开发者如何维护本地服务与身份

### 14.1 先认识现有环境

截至侧栏版交付核验，前端 3000 使用 `.next-workbench` 生产目录，后端 8000 使用单 worker。日志和 PID 文件在 `backend/var/service/`；默认数据库 `backend/var/agent/runs.sqlite3`，访问配置 `backend/var/eval/access-keys.json`，私有明文凭证 `backend/var/eval/access-credentials.txt`。

这些是已记录的交付状态，不能代替实时健康检查。开始测试前核对页面、`GET /api/health`、带身份的 `GET /api/eval/me` 和 `GET /api/eval/config`；若启动命令覆盖了 `AGENT_TRACE_DB` 或 `EVAL_ACCESS_FILE`，以实际设置为准。

工作台开启需要 `EVAL_ENABLED=true`；关闭时相关接口返回 404。启用但身份配置缺失/损坏会启动失败，不会匿名放行。工作台密钥只在前端内存中，刷新需重新登录。

### 14.2 配置身份

仅在**全新环境**或新的配置目录生成初始身份。以下命令从 `backend/` 运行，示例目录须不存在已有身份文件：

```bash
.venv/bin/python scripts/create_eval_access.py \
  --tester tester_zhang --tester tester_li \
  --developer developer_wang --reviewer expert_chen \
  --directory var/eval-new-environment
```

脚本只打印文件路径，不输出密钥，且拒绝覆盖已有身份文件。它不是向现有身份文件追加用户的管理工具。现有环境新增/轮换身份，需管理员备份后维护经 `AccessFile` 校验的用户列表，保留既有身份与令牌摘要，不删除文件重建冒充无损升级；本轮还没有相应管理 UI。

服务端存 `tester_id`、角色和 token SHA-256；每人身份唯一、token 摘要唯一。给新配置指定 `EVAL_ACCESS_FILE`，并在约定窗口重启后生效。普通聊天接口和临时附件接口目前仍不是完整账户隔离体系。

### 14.3 改动、构建与切换顺序

1. 阅读相关目录规范，检查工作区差异。现有未提交改动和历史库必须保留，不能用重置清理。
2. 在临时端口和独立数据库验证新代码，合成 fail/pass 不写正式库。
3. 前端使用独立构建目录。当前 `.next-workbench` 正在供正式服务使用时，不向其中构建；可选择未被服务使用的 `.next-candidate`，先核对是否空闲。
4. 完成相应后端/浏览器/类型/构建检查后，生成新的源码清单。当前脚本的交付前缀固定含 20261004，这是现有工具行为，后续调整命名须连同启动脚本核对。
5. 对正式库、身份配置和外部资产做当前备份，验证可恢复。不要使用一份早于新人工记录的旧备份声称已保护最新数据。
6. 协调测试窗口，核对现有进程后有序停止，使用新清单和已验证构建目录启动。
7. 检查健康、登录、`/api/eval/config`、原执行/评分/Run 和资产可读性，记录新构建后再恢复人工测试。

## 15. 备份、恢复、证据导出

数据库和外部资料分开考虑。内存会话、临时上传和运行中的协程没有可恢复快照；重启后需重置/重传或重新重跑。

以下命令从 `backend/` 运行。目的地必须是新的目录或文件，请每次使用不同的批次名。命令示例仅供操作时执行，不表示本文已发起备份。

```bash
.venv/bin/python scripts/eval_archive.py backup \
  --database var/agent/runs.sqlite3 \
  --access var/eval/access-keys.json \
  --credentials var/eval/access-credentials.txt \
  --destination var/backups/example-new-batch

.venv/bin/python scripts/eval_archive.py verify \
  --bundle var/backups/example-new-batch

.venv/bin/python scripts/eval_archive.py restore \
  --bundle var/backups/example-new-batch \
  --destination var/backups/example-new-batch-restore-check

.venv/bin/python scripts/eval_archive.py export \
  --database var/agent/runs.sqlite3 \
  --destination var/backups/example-new-batch-evidence.json
```

`backup` 使用 SQLite 在线备份包含已提交 WAL 数据，保存身份文件及可选私有凭证；`verify` 核对文件、数据库结构和表内容指纹；`restore` 只写新目录，不覆盖当前库，也不自动把服务切到恢复库；`export` 导出 Run/eval 数据供审阅，不带身份密钥，但仍含问题、回答和材料路径。

**此备份不含外部资产、模型和索引文件。**还需单独保存 `data/eval/uploads/`、Case 引用原件、论文/审核材料、必要索引/模型或可重复生成方法，以及相应源码和配置。资产库只存路径和指纹，恢复一个数据库不会凭空恢复文件。

现有侧栏交付留档：源码清单 181 项，私有源码包 `backend/var/backups/delivery-20261004-ee879b36e1ab-source.tar.gz`；切换前备份 `backend/var/backups/pre-sidebar-switch-20261004/`，恢复验证副本为同路径加 `-restore-check`。备份当时 34 条 Run、3 条执行、2 条评分，切换后全部旧表行原样保留。这些是历史快照数量，实时库可继续增长。

## 16. 常见问题与排查顺序

| 现象 | 优先检查 |
|---|---|
| 页面开了但后台请求失败 | API 地址是否匹配、8000 健康、CORS、是否旧前端构建 |
| 评测 API 404 | `EVAL_ENABLED`、是否启动了旧后端；不等于数据库丢失 |
| 401 / 登录失效 | 本人密钥、Bearer 格式、服务当前加载的访问文件；刷新需重登 |
| 403 / 看不到操作按钮 | 角色、执行所有者、页面模块；developer 也不能代改他人执行 |
| Task 配置不匹配 | 实际 `/config` 与冻结 Task；新构建创建新任务 |
| 上传指纹不符 | 原件内容和名称、Case fixture；不要直接改冻结标准 |
| Case 发布被拒绝 | 版本号、附件原件、未保存改动、多人修订冲突 |
| 评分不能通过 | 缺必选项、无有效操作、缺 Trace、任务 Run 版本不一致 |
| Issue 登记失败 | 是否 partial/fail、是否选了带 Run 的提问事件 |
| Issue 复测关联失败 | 是否同 Case 版本的新执行、是否已评分、是否已关联别的问题、实际版本是否一致 |
| 回归受阻 | 原件路径/指纹、人工事件、附件资源上限；读明确的阻塞步骤 |
| 重启后上下文消失 | 预期的内存生命周期；旧 DB 记录仍在，新上下文要重置重传 |
| 资料已上传但问答没引用 | 资产登记不是 RAG 入库；检查索引和检索链路 |
| 统计看似变好 | 核对分母、Case 版本、重复执行、评分人群和待评分/受阻比例 |

技术定位建议顺序为：身份与环境 → 正确的执行/Run → 版本 → 路由/状态 → 工具 → 证据 → 答案 → 评分/统计。避免在找错环境或看错轮次时调整模型参数。
