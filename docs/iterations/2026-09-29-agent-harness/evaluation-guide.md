# 评测工作台使用说明

> 2026-10-05：面向当前侧栏版的完整操作说明已拆为[测评者使用说明书](tester-user-manual.md)和[开发者使用说明书](developer-user-manual.md)。第一次使用请先读对应版本；本文保留早期技术说明，部分面板名称和入口属于旧布局。

本机入口：[http://localhost:3000/evaluation](http://localhost:3000/evaluation)。
当前实现用例执行、独立评分、开发者 Trace、评分分布与回归版本比较，不替代专业审核。
这是基础工作台的操作说明；完整后台的未完成事项及文档入口见 [最新交接](handoff-2026-10-04.md)。

## 登录

本机已生成两个独立身份：`local-tester`（测试者）、`local-developer`（开发者）。
密钥在本机私有文件 `backend/var/eval/access-credentials.txt`，复制对应行冒号后的密钥登录。
文件权限为 600，受 Git ignore 保护。服务端 `access-keys.json` 只存密钥摘要及角色映射。
不要把开发者密钥给测试者，也不要把密钥写进评分备注。

网页只在内存中保存密钥；刷新后重新登录，可以从执行列表打开自己的已有记录。
测试者看不到其他测试者的执行和开发者 Trace；开发者可以查看全部记录，
但不能代替别人继续执行或提交评分。权限由服务端检查。

## 测试者：执行并评分

1. 选择用例和版本，点击“新建一次执行”。用例数量以当前数据库和页面为准；
   默认选项同时列出历史版本，必须按所选版本的标准判断。
   当前分阶段上传选 F02/B02/B03 v3，省略追问选 F05 v2，组合问答选 NEW02 v3。
2. 阅读前提、步骤、通过标准和所需附件。原表和错误样本按清单准备，
   指定附件会校验文件名和 SHA-256，避免拿另一张表套用既定数值标准。
3. 在该执行内上传附件并逐轮发送问题；“填入问题”只填表，不会自动提交。
   所有提问、错误、附件操作、手动备注按顺序保存。
   同一执行上传一次即可，后续提问自动复用，刷新页面也不需要重新上传。
   持续提问会延长有效附件的闲置期限；替换上传失败保留原附件，成功后才切换。
4. “重置上下文”清除当前附件、指标和对话状态，仍保留本次执行中的历史证据。
   “移除附件”只移除当前附件。服务重启或上下文闲置过期后，必须先重置并重传，
   不会假装旧临时状态仍有效。
5. 明确选择总体结论和路由、工具、证据、答案四层评分，记录问题原句、依据和修改建议。
   可用性 1–5 分可选。部分通过、不通过和受阻必须写原因。
6. 提交后冻结本次执行及评分，不覆盖历史。复测新建执行。

总体“受阻”时四层选择“不适用 / 无法判断”，说明缺少的条件。
没有可执行材料时允许直接提交受阻；正常评分需要至少一次提问或上传操作。
只检查上传的用例可以按上传事件评分，系统不会为它虚构聊天 Run。
Trace 保存失败的执行只能标为受阻或另建执行，不能静默计作通过。

附件为 10 MiB 上限。超限文件的前端拦截、浏览器刷新等人工步骤可写操作备注；
备注只证明测试者记录了操作，不等于自动验证通过。

## 开发者：定位问题

开发者拥有测试者操作能力，同时能查看全部执行、运行列表、Trace 和评分分布。
从某一轮的“查看 Trace”进入，检查路由、工具状态、错误码、运行前后状态、证据、
答案与证据关联，以及构建/配置版本。记录不包含模型思维链、访问密钥或文件 bearer token。

运行的 `status=ok` 表示请求执行完毕；`outcome=partial` 仍表示任务有未完成部分。
两者分别显示，不能凭 HTTP 200 或 status 推算用户任务成功率。

### 如何读“运行详情”中的 Trace

在“本次执行”里点某轮的“查看 Trace”。**一个 Run／Trace 只对应一轮提问**；一次执行可以
先有上传事件，再有多轮 Run。上传、移除附件和手动备注本身不是问答 Run。
“完整执行记录”是这一轮 Trace 的完整 JSON，其他折叠栏是从中挑出的字段。
建议按“路由 → 工具与错误 → 运行前后状态 → 证据 → 回答 → 未完成部分”阅读。

| 完整记录字段 | 含义与何时为空 |
|---|---|
| `run_id`、`input`、`started_at` | 本轮唯一编号、问题原句、开始时间；排查时用 Run ID 定位具体轮次。 |
| `conversation_ref` | 会话 ID 的摘要；相同值表明同一会话，不是可复用的原始会话密钥。 |
| `schema_version`、`harness_version` | Trace 数据格式和运行框架版本。 |
| `config_version` | 构建标识和启动时版本清单摘要；相同标识表示所记录的指纹相同，具体覆盖范围看 `config_manifest`。 |
| `config_manifest` | 启动时冻结的 Agent、Prompt、Retriever 代码、依赖锁、回答配置、索引和本地模型文件身份。`content_hashed` 才有内容 SHA-256；超过 256 MiB 的目录为 `metadata_only_size_limit`，仅记录路径、大小、修改时间摘要。外部 LLM 只记录声明的模型名，服务商实际权重未验证。旧 Run 可为 `{}`。 |
| `status` | 程序状态：`running`、`ok`、`error`、`cancelled`；持久化的已结束 Run 通常为后三者。`ok` 仅表示请求完成，不表示答案正确。 |
| `outcome` | 任务结果：`complete`、`partial`、`clarification`（需要用户补充信息）；运行报错时可为 `null`。`status=ok` 与 `outcome=partial` 可以同时出现。 |
| `answer`、`model` | 本轮回答及生成它的模型或处理器；失败时可为 `null`。文件计算显示 `whcns_balance_reader`，不表示重新运行 WHCNS 模型。 |
| `latency_ms`、`error_code` | 本轮总耗时及错误码。正常时错误码通常为 `null`；总耗时不必等于各工具耗时之和。 |

各折叠栏对应以下内容：

1. **路由 `decision`：**`route` 是最终处理路径：`FILE_ANALYSIS` 算表格、`KNOWLEDGE`
   查文献、`COMPOSED` 组合文件和文献、`CLARIFY` 要求补充、`DIRECT` 直接说明能力、
   `OUT_OF_SCOPE` 回应能力范围外问题。`reason_code` 记录判定原因，如 `file_intent`、
   `inherited_metric`（“那最小值呢？”继承上一轮字段）。`skills` 是计划的工具列表；
   是否真的调用须看 `tool_calls`。运行中发现附件无效或问题不明确时，最终路由可能改为
   `CLARIFY`。若请求在路由前失败，`decision` 可为 `null`。
2. **工具与错误 `tool_calls`：**每项的 `skill` 是实际调用的工具，`status` 为 `ok`、
   `clarification`、`error` 或 `cancelled`，`latency_ms` 是该工具耗时，`error_code` 只在
   失败时通常有值。文件问答常见 `file_inspector` 和 `whcns_analyzer`，文献问答常见
   `knowledge_search`。工具 `ok` 只说明调用完成，不能代替答案和证据核对；路由前失败时
   此列表可能为空。
3. **运行前／后状态 `state_before`、`state_after`：**`crop` 是明确设置的作物约束；
   `current_metric` 是可供追问继承的字段；`current_operation` 是最近的 `min`／`max`；
   `last_tool` 是上次工具；`attachment_ref` 是临时附件标识的摘要，**不是文件内容 SHA-256**。
   未设置的状态为 `null` 或空列表；若请求在取得会话状态前失败，`state_after` 可为 `null`。
4. **证据 `evidence`：**每条 `evidence_id` 可供答案片段关联。`source_type=file`、
   `status=computed` 表示从已上传输出表计算的值：`claim_or_value` 是数值，`unit` 是单位，
   `source_id` 是文件内容指纹，`location` 包含 `sheet`、数值 `cell`、日序 `day_cell`、
   `model_day`、`data_range`、`occurrences`；`provenance` 包含文件名、字段、操作、工具版本等。
   `source_type=literature`、`status=retrieved` 表示检索到的文献片段：`source_id`／
   `location.chunk_id` 定位片段，`location.citation_index` 对应回答中的 `[1]` 等编号，
   `provenance.source` 是来源文件。**检索到片段不代表它支持回答的每个断言**，要读原文核查。
   直接能力介绍、澄清或失败回答没有证据时，此列表为空可能正常。
5. **答案与证据关联 `sections`：**`kind` 可为 `file_observation`（文件观察）、
   `literature_inference`（文献推断）、`limitation`（局限）；`content` 是该段文字；
   `citation_indices`、`file_evidence_indices` 和 `evidence_ids` 把段落连到上方证据。
   普通文献回答和简单文件极值回答也可能是 `[]`，须继续看 `evidence`，不能因空数组
   直接判断“没有证据”。
6. **未完成部分 `warnings`：**每项有供程序定位的 `code` 和供人阅读的 `message`。
   完整回答通常为 `[]`。组合问答若文件计算成功而文献步骤失败，可能仍有回答、
   `status=ok`，但 `outcome=partial` 且这里有警告。

**F05 v2 两轮例子：**第一轮“leak_NO3 最大值及对应日序”走 `FILE_ANALYSIS`，
`file_inspector`、`whcns_analyzer` 均为 `ok`；`state_before.current_metric=null`，
运行后变为 `leak_NO3`／`["max"]`；文件证据给出约 3.6593、模型日序 283、
`Nbal_out!C284/A284`。第二轮“那最小值呢？”的 `reason_code=inherited_metric`，
运行前已经记住 `leak_NO3`，运行后操作变为 `min`；证据为 0、首次日序 2、
`Nbal_out!C3/A3`、191 条并列。这两轮 `sections=[]`、`warnings=[]` 是正常现象。

人工评分时，路由看 `decision`，工具看实际 `tool_calls`，证据看 `evidence` 和原件，
答案须逐轮对照当前用例的通过标准。Trace 提供可复查线索，不自动作出专业结论。

统计以独立执行的已提交评分为单位，每次执行最多一份评分：

- 待评分执行单列；blocked 单列且不进入四层分母。
- 每层 n.a. 不入该层分母；yes、partial、no 分开计数。
- 按用例版本分组，不把 v1 与 v3 的标准当成同一标准。
- 当前统计是开发试评分布，不是专业准确率，也不是正式独立测试集成绩。

已保存的第二批真实联调在独立目录 `backend/var/eval/harness-20260929-091313/`，
未自动导入当前工作台数据库；审核该次答案请使用
[冻结回答](professional-review-snapshot.md) 和 [10 项清单](professional-review-checklist.md)。
工作台新执行产生新的回答，不能替代旧快照的审核。

## 开发者：保存回归基线与比较版本

1. 打开一项已完成提问的执行，在“回归样例与版本比较”填写标题和备注，
   点击“保存为回归基线”。可以保存尚未评分的执行；基线需要 1–20 轮提问。
   当前用例、执行、Trace 和已有评分会冻结，后续操作不改写基线。
2. 在对应样例点击“用当前版本重跑”。系统会建立一项新执行、依原顺序还原提问和附件操作，
   显示进度；最多同时两项。可以取消，已完成步骤仍保留。运行期间不可手工修改或评分该执行。
3. 点击“比较结果”，逐轮查看基线和新回答、路由、工具、文件证据、引用、错误、耗时及配置标识。
   没有完成的轮次明确显示未执行；“重跑完成”只表示步骤执行结束，不表示答案正确。
4. 点击“打开新执行 / 人工评分”，核查后独立提交新评分。原评分不被覆盖，
   自动重跑不会生成评分。提交新评分后再次点击“比较结果”可读取新评分。
5. 更新代码并以新的 `AGENT_BUILD_VERSION` 启动后，对同一基线重跑即可比较版本。
   相同版本重复生成也可能有文字差异；对比时检查 `config_manifest` 的逐项状态。

自动重跑只支持提问、重置上下文、移除附件和成功上传。
附件必须是冻结 Case 中登记的本地原件（种子用例来自 `manual_cases.v1.json`，新发布用例来自资产目录），且 SHA-256 与基线一致；
每份不超过 10 MiB，整次最多 64 MiB。缺材料、文件变化、人工步骤或无法复原的上传失败
会在已完成的可自动步骤之后显示“受阻”及 `blocked_step`，不会跳过人工步骤；
例如三轮提问后第四步为人工备注时，前三轮各保存独立新 Run，第四步等待人工复测。
如果第一步就不可复原，新执行没有伪造的运行记录。此类用例仍在工作台手动复测。
重启将未完成任务标为中断，需要新建重跑；旧数据和完成步骤保留。

## 如何理解基线、重跑和评分

**用例**是固定的提问步骤和预期标准，不是已经跑出的答案。**执行**是按某个用例实际上传、
提问后留下的事件、回答和 Run 记录。**回归基线**是从一次执行保存的快照，用来与后续执行比较。
用例不会自动带有执行结果或评分；已有多少执行、评分和基线，以当前工作台数据库为准。

- 不必给每个用例都建基线。只做一次验收时，可以新建执行并直接人工评分；需要以后反复比较的
  关键用例，先人工跑出一份结果并保存基线。此后该基线可以多次自动重跑。
- 比较的主要用途是观察代码或配置改动前后的表现。未改动时也可重跑，检查重放流程和文件计算
  是否稳定；模型生成的措辞、引用和耗时可能变化，因此“有差异”不等于变好或变坏。
- 每次重跑都会建立新执行。人工评分只写入这次执行的评测记录，不会覆盖原执行的评分，
  也不会自动修改代码、训练模型或改变后续回答。是否据此修改系统，由开发者判断。
- 评分统计用于看已评分执行的总体结论，以及路由、工具、证据、答案各层的通过、部分通过和
  不通过分布。改进后希望可比用例的问题减少，但应在相同用例版本和评分标准下比较；
  新增难题会改变评分样本构成，不能只看一个通过比例判断进步。待评分和受阻执行单列，
  不能算通过，也不进入四层评分的通过率分母。

**RG04 手动步骤示例：**另建执行并提问后，手动将浏览器窗口缩至约 375px，检查回答和附件区
是否横向溢出，再添加“已缩窄窗口并人工检查排版”的操作备注，保存为另一条基线。
服务器能保存这条备注，却无法自动操作浏览器窗口或判断排版。重跑遇到该步骤应显示“受阻”，
等待人工复测；它与已有基线不冲突，也不能被跳过后自动记为通过。

## Task、Issue、复测与审核身份

开发者可将当前用例版本、构建版本和知识库版本冻结为 Task。测试者选择该 Task 后新建执行，
系统同时记录服务器实际运行配置指纹和版本清单，以及知识库路径、集合、嵌入/重排序模型配置；
新建执行以及继续提问、上传、重置和移除附件时都会核对任务配置。服务器配置改变后，
旧执行可查看、记录手动说明和评价已保存的证据，但不能混入新配置下的运行。
若历史 Run 已混用配置，只能记录受阻；复测应新建对应版本的 Task 和执行。知识库版本标签由开发者声明，
启用 RAG 时，启动清单会对不超过 256 MiB 的本地索引计算内容指纹；更大的索引和模型目录只记录元数据指纹，不能据此断言内容相同。运行和开发试评照常保存；
任务只关联用例和执行，不预设通过。已评为部分通过或不通过的执行，
开发者可选具体提问轮次登记 Issue。系统从事件提取原问题、Run ID、回答或错误、Review ID，
连同负责人和证据备注保存。修复后在同一用例版本新建执行并提交独立评分，最后为 Issue 关联
复测执行、修复版本和复测结论。Issue 原记录、旧 Run 和旧 Review 均保留。
修复版本须与复测 Run 的实际构建名或完整配置标识一致；系统从保存的 Run 核验，
不使用关联时服务器的当前版本替代。没有 Run、缺失 Trace 或混用配置的复测不能作为有效通过。
问题列表展示复测次数及原执行/复测执行入口。看板只有在最近一次复测通过且版本已核验时
才将问题计为已解决；后续失败或受阻会再次显示待解决，旧记录保留。

普通执行评分的 `review_kind=development_trial`。开发者可以把有明确材料路径、SHA-256 和依据的
AI 辅助复核另存为 `ai_assisted`；该记录**不会**将用例标记为专家审核。只有由管理员在访问文件中
配置的 `reviewer` 身份才能保存 `domain_expert` 审核。审核历史保留审核人、角色、时间、结论、
材料与可选关联执行。工作台统计分别显示开发试评分布、AI 辅助记录数、专家记录数，
不合并成“专业通过率”。历史 PR01–PR10 CSV 仍是 AI 辅助复核来源材料；其核查点跨多条用例，
未臆造一对一 Case/Run 关联。

新版 `K01@4` 验证文章题名、正文摘录和机制支持；`RG04@1` 验证逐步重放。
两者是新验收版本，尚未由人工提交通过评分。主聊天页已实现多文件选择和逐文件状态，规则见

## 开发者：资产目录与 Case 版本

在工作台的“Case 与数据资产目录”登记 `data/` 或 `docs/` 下的原件路径、来源和备注；服务器计算并保存 SHA-256。模型输入与输出先保存候选配对。只有 `reviewer` 身份可选择候选配对、证据资产并写核实依据，保存一条独立的“专家核实”记录。系统核对身份、资产类型和证据指纹；证据材料是否真的证明输入输出关系仍需审核人阅读判断。
提交核实前会重新计算输入、输出和证据三份原件的 SHA-256；文件已改变时须重新登记和核查。

开发者可复制当前 Case 到草稿，编辑 JSON 标准并关联已登记的结果表资产。每次保存生成新修订，历史可查；发布前服务器再次核对附件原件指纹，只允许高于现有最高版本的新版本。发布后原 Case、执行和评分不变。工作台测试执行仍一次使用一个附件；多文件主聊天规则不自动改写旧 Case 标准。
编辑内容、附件选择或备注有未保存修改时，发布按钮不可用。发布请求须携带已打开的
`expected_revision`；其他人保存新修订后，旧页面会收到冲突提示。点“重新打开已保存修订”
会替换本地未保存内容，核对后才能发布该修订；普通刷新目录不会悄悄更换编辑基准。

## 启动与数据位置

后端需要 `EVAL_ENABLED=true`，默认关闭，未启用时评测接口返回 404。
启用时缺少或损坏的身份文件会导致启动失败，不会降级成匿名可访问。
首次为新环境生成身份（已有文件不会覆盖）：

```bash
# backend/
.venv/bin/python scripts/create_eval_access.py --tester local-tester --developer local-developer --reviewer local-expert
env EVAL_ENABLED=true AGENT_BUILD_VERSION=local-eval \
  HF_HUB_OFFLINE=1 TRANSFORMERS_OFFLINE=1 DEEPSEEK_PROXY=http://127.0.0.1:7890 \
  .venv/bin/python -m uvicorn src.main:app --host 127.0.0.1 --port 8000 --workers 1
```

本机模型直连受限，真实知识问答需沿用 `DEEPSEEK_PROXY=http://127.0.0.1:7890`，
使用本地模型时同时设 `HF_HUB_OFFLINE=1 TRANSFORMERS_OFFLINE=1`。
正式采集评测时将 `local-eval` 替换为实际源码快照标识，以便比较版本。
端口已占用时不要重复启动。常驻服务不一定已加载工作区最新代码；正式复测前核对
`/api/eval/config`、实际构建和数据库位置，不能从本文推断实时服务版本。

`EVAL_ACCESS_FILE` 默认 `backend/var/eval/access-keys.json`；
`AGENT_TRACE_DB` 默认 `backend/var/agent/runs.sqlite3`。
Case、Task、Execution、Event、Review、Issue、复测、独立审核、Regression、Replay 与 Run 共享该 SQLite，运行记录及评分持久化；
临时附件和对话上下文仍在内存，单 worker。更换数据库也会切换可见执行与评分。
