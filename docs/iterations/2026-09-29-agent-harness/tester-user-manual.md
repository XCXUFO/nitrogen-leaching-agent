适用对象：第一次使用平台的测试者、产品验收人员，以及参与独立专业审核的领域专家。更新日期：2026-10-05。本文按侧栏版 `delivery-20261004-ee879b36e1ab` 的实际功能编写；版本变化后，以开发者确认的当前环境为准。

## 1. 这个平台是做什么的

农业模型助手的前台，是用户直接提问、上传结果表和阅读回答的地方。测评工作台则用来判断：助手在指定条件下有没有正确理解问题、选对处理方式、给出有依据的答案，改进后是否真的变好了。

例如，用户上传一张氮平衡结果表并问“硝态氮最大值及日序”。仅看到一段流畅回答还不够。我们需要知道数值是否来自该文件、单位是否正确、日序是否定位到正确单元格、追问有没有沿用正确字段、缺材料时是否诚实说明。

工作台把这些判断变成可以协作、追踪和重复验证的记录：

| 要解决的问题 | 平台提供的办法 | 对测评者的意义 |
|---|---|---|
| 不知道该测什么 | 用例写明前提、步骤、原问题与通过标准 | 按同一标准测试，减少临时猜测 |
| 多个人测的不是同一版本 | 任务固定用例版本和运行配置 | 知道结果属于哪次交付 |
| 只记“感觉不好”，开发者无法复现 | 执行保存操作、问题、回答、错误和 Run ID | 能精确指出出错轮次 |
| 改完以后不知道是否修好 | 新执行、新评分、问题复测关联 | 保留改前改后的证据 |
| 程序测试和专业判断混在一起 | 普通试评、AI 辅助复核、专家审核分别记录 | 清楚区分“运行正常”和“专业正确” |

当前是农业模型助手的研发与质量管理工作台。它已经具备基础闭环，但还没有完整企业用户管理、所有任务一键自动执行、正式发布审批等能力。它也不会因为你打了分就自动训练模型、修改提示词或改变下一次回答；开发者需要根据证据实施改进。

## 2. 它与前台 Agent 是什么关系

可以把整个系统理解为三层：

```text
使用入口
  前台聊天：用户自由提问、上传文件、检查真实页面体验
  测评工作台：按用例组织测试、保存过程、评分与协作
                       ↓
共同的 Agent 服务
  判断问题 → 读取结果表 / 检索文献 / 组合回答 / 要求补充
                       ↓
证据与记录
  文件计算依据、文献引用、每轮 Run、后台执行与评分
```

两边调用同一套 Agent 处理能力，但会话和操作记录不自动合并。

| 场景 | 应在哪里做 | 留下什么 |
|---|---|---|
| 检查输入法、快捷键、聊天滚动、拖入多个文件 | 前台聊天 `/` | 问答产生 Run；人工现象记共编验收文档 |
| 按 F05 v2 测上传、最大值、追问最小值并评分 | 工作台“执行记录” | 一个 Execution，多个操作事件和问答 Run，一份冻结评分 |
| 阅读原文，判断某条农业机理是否成立 | 审核队列及原始材料 | 专家的独立审核记录，或共编文档中的真实审核意见 |

**前台聊天不会自动生成后台 Execution，也不会自动生成评分。**你在前台刚问完一句话，去后台执行列表找不到它是正常的。开发者可在“运行记录”中查该 Run；若需要完整用例评分，另建后台执行，明确这是一次新的运行，不能说它就是前台当时那次回答。

主聊天目前可保留最多 5 份文件，每份不超过 10 MiB、合计不超过 40 MiB；每轮只分析选中的一份。后台一次执行当前只维护一份附件。因此，多文件选择器的体验必须到前台测。

## 3. 先认识这些名称

| 名称 | 通俗含义 | 例子与注意事项 |
|---|---|---|
| Case／用例 | 一张测试说明卡 | `F05@2` 或 `F05 v2` 都表示 F05 第 2 版；不是一次测试结果 |
| Task／任务 | 某次交付要测的一组固定版本用例 | “文件问答验收第 1 轮”；由开发者创建，可含多条 Case |
| Execution／执行 | 某个人实际做的一次测试 | 同一 Case 可以有多次执行，每次有独立编号 |
| Event／操作事件 | 执行中的一步 | 上传、提问、移除、重置或手动记录；事件序号不等于问答轮次 |
| Run／运行 | Agent 处理一轮问题的记录 | 上传后连问两句，通常是一个执行、两个 Run；上传本身不是 Run |
| Review／开发试评 | 执行者对这次执行提交的评分 | 普通测评者提交的也叫“开发试评”，不表示提交者必须是开发者 |
| Assessment／独立审核 | 对材料和回答的另一类核查记录 | AI 辅助复核与领域专家审核有不同身份 |
| Issue／问题 | 将失败轮次、证据、负责人和复测串起来的问题单 | 当前由开发者登记；普通测评者交付失败执行和依据即可 |
| 回归基线 | 保存下来供以后比较的一次执行快照 | 后续重跑产生新执行，旧回答和旧评分不变 |
| SHA-256／文件指纹 | 对文件内容计算出的标识 | 同名文件可能指纹不同；重命名通常不改内容指纹，但用例还可能检查文件名 |

“已评分”表示已提交记录，不表示通过。“已有专家审核”表示存在专家记录，也不保证专家结论是通过。请打开实际结论和依据。

## 4. 第一次登录与认识导航

### 4.1 开始前准备

请向负责人取得：测试环境地址、你自己的访问密钥、任务名称或链接、指定 Case 版本、附件原件、结果记录文档地址。缺少材料就如实记录，不必自行拼凑输入输出。

本机入口是 `http://localhost:3000/evaluation`，前台聊天是 `http://localhost:3000/`。`localhost` 指你正在使用的这台电脑；其他同事不能在自己的电脑上输入此地址访问项目机器。远程协作需开发者提供可访问地址，当前本地启动方式不等于已部署多人在线服务。

在工作台登录框输入自己的访问密钥。项目机器上的私有凭证文件是 `backend/var/eval/access-credentials.txt`，由开发者分发相应身份的密钥。不要将整份凭证文件或密钥贴入多人文档。多人应使用不同身份，否则平台无法区分是谁执行和评分。

### 4.2 登录后的行为

左侧显示当前身份可用的菜单，顶部可查看身份并退出。桌面可以收起侧栏；窄屏通过菜单按钮打开抽屉，选择模块后收起，也可按 Escape 关闭。

客户端切换模块通常不需要重新登录。刷新或重新打开页面后需再次输入密钥，原详情地址会保留。页面中未提交的输入、评分草稿不要依赖刷新恢复；已保存的事件和评分由服务器保留。

### 4.3 普通测评者能使用什么

| 入口 | 用途 | 操作范围 |
|---|---|---|
| 工作台总览 | 找到任务、用例、执行入口 | 查看当前身份可见的近期执行与待评分情况 |
| 任务管理 | 找到本轮测试安排 | 查看任务、准备自己的执行、查看自己的进度 |
| 用例库 | 阅读标准 | 按编号/标题、类别、审核状态筛选并查看指定版本 |
| 执行记录 | 做测试并评分 | 创建、继续和评分自己的执行，查看历史记录 |

普通 `tester` 没有回归对比、问题管理、运行 Trace、资产管理和审核队列菜单。不要为了“看到所有功能”借开发者身份代测。`reviewer` 是独立专业审核角色，另有审核队列和资产目录入口，见第 9 节。

## 5. 完成一次后台测试

### 5.1 通过任务开始：适合正式批次

1. 点“任务管理”，按任务标题、编号或构建检索，点“查看任务”。
2. 核对任务名称和 Case 版本。若提示“当前服务配置与冻结任务不同”，将情况反馈给开发者；新版本需要新任务，不要把新结果混进旧任务。
3. 点“批量准备我的执行”。它只为你补齐缺少的执行记录，**不会自动上传、提问或评分**。重复点击不会为同一任务中的已有个人用例执行再造重复记录。
4. 在对应 Case 下点“打开执行”。需要重新测试时应另建执行，不靠重复点“批量准备”生成复测。
5. 批量准备的全新执行首次打开即可开始，无需先重置上下文。已有操作的执行若提示临时上下文不可用，点“重置上下文”，再按用例从所需步骤开始并重传附件。任务内执行的详情返回按钮会返回所属任务，方便继续下一项。

任务进度中的“已准备”“已开始”“已评分”分别回答有没有记录、有没有操作、有没有提交评价。不能把“已评分 3 个”理解成“3 个都通过”。

### 5.2 直接从用例开始：适合单项验证

1. “用例库”检索用例，例如 F05，找到要求的 v2，点“查看用例”。
2. 阅读前提、每个步骤、通过标准。
3. 点“使用此版本新建执行”，核对“用例版本”和“所属任务”。从用例进入不会自动替你选择正式任务。
4. 有任务要求时选择相应任务；临时探索可选“独立执行（无任务）”。独立执行不会自动归入某个任务的进度。
5. 点“新建一次执行”，记录页面中的 Execution ID。

也可从“执行记录 → 新建执行”进入同一表单。切换用例版本后，所属任务会清空，需要重新选择。

### 5.3 执行页面怎么用

| 页面区域或按钮 | 你应该做什么 | 保存的内容 |
|---|---|---|
| 前提、步骤、通过标准与附件指纹 | 操作前展开并阅读 | 标准属于固定 Case 版本 |
| 上传本用例附件 | 选择指定原件，检查成功/失败状态 | 文件名、指纹、状态或错误；不会自动分析所有问题 |
| 填入问题 | 把 Case 中的原句填入输入框 | 仅填入，不等于已发送 |
| 发送本轮 | 核对原句后发送，等待响应再继续 | 本轮问题、回答/错误、Run ID |
| 移除附件 | 按用例要求清除当前文件 | 留下移除事件；后续不能假装文件仍在 |
| 重置上下文 | 开始新上下文，随后按需重传附件 | 留下重置事件；不会删除之前的事件 |
| 手动操作记录 → 保存操作记录 | 写真实做过的刷新、等待、缩窗等动作及现象 | 保存文字说明，不替你执行浏览器动作 |
| 提交本次评分 | 按第 6 节逐项判断 | 提交后冻结执行和评分 |

上传仅接受 `.xls`、`.xlsx`，每份不超过 10 MiB。后台当前只维护一个当前附件；上传另一份时不要假设上一份仍可引用。用例登记了指定文件时，文件名或内容指纹不一致会被拒绝。

操作过程按时间排列。上传、重置、手动备注没有问答 Run 很正常。看到错误时保存实际错误和发生位置，不要不断重试直到成功后才记“通过”；后续重试应在记录中明确体现。

### 5.4 检查答案和证据

文件答案至少核对：分析的是哪个文件、哪个字段、什么运算、数值和单位、模型日序、表名和单元格、数据范围、并列极值说明。

文献答案至少核对：是否回答原问题、引用能否定位、题名和正文是否可读、被引用段落是否支持这句话、作物及情景是否适用。题目看起来相关，不等于正文支持断言。

组合回答应区分“表中算出的事实”“一般文献中的可能机制”“缺少哪些材料”。如果缺同期天气和管理记录，不能因为回答听起来合理就确认某一天的真实原因。

## 6. 如何评分

### 6.1 总体结论

| 选项 | 什么时候选 | 示例 |
|---|---|---|
| 通过 | 本次实际检查满足用例标准，没有已知失败项 | 两轮数值、单位和单元格均正确，所需说明齐全 |
| 部分通过 | 核心内容部分满足，仍有明确不足 | 最大值正确，但漏了用例要求的并列次数 |
| 不通过 | 关键标准未满足 | 用错字段、给出错误值或编造依据 |
| 受阻 | 缺材料、环境或可靠记录，无法完成判断 | 没有指定原件、服务不可用、Trace 保存失败 |

明确发生的功能失败通常应按实际标准记不通过；“受阻”用于无法进行或无法可靠判断，不能用来掩盖一个已经确认的错误。若缺少专业判断能力，在相应维度选“不适用 / 无法判断”，写清尚待专家核实的部分。

### 6.2 四个维度

| 维度 | 判断的问题 | 普通测评者如何取证 |
|---|---|---|
| 路由是否正确 | 本该算表、查文献还是追问，系统选择合适吗？ | 结合回答路径和可见行为；无法确认内部路由时选无法判断，请开发者查 Trace |
| 工具使用是否正确 | 是否使用了正确资料和计算能力？ | 看文件证据、字段、操作；无法观察工具细节时不猜测 |
| 证据是否支持 | 单元格/原文真的支持结果或断言吗？ | 打开原件核对；允许“部分” |
| 答案是否正确 | 是否满足该版本通过标准？ | 按标准逐条核对；允许“部分” |

路由和工具选项为“是 / 否 / 不适用或无法判断”；证据和答案另有“部分”。可用性 1–5 分可选；团队若使用此项，应事先统一尺度，例如 1 表示严重阻碍任务、3 表示能完成但有明显困难、5 表示过程顺畅。这是建议口径，不是系统自动打分规则。

表单规则：

- 总体和四个维度都要明确选择。受阻时四项都选“不适用 / 无法判断”，并填原因。
- 总体通过不能同时有“否”或“部分”；非受阻时至少判断一个维度。
- 部分通过、不通过必须填说明。说明写问题原句、实际结果、预期、证据位置。
- 问题标签用逗号分隔，最多 10 个，每个不超过 80 字；例如“追问丢失字段,引用不支持”。
- 正常评分前至少有一次提问或上传。只有手动备注的页面验收应主要记在共编文档，不应为了满足表单随意制造问答。
- 点击“提交并冻结评分”后不能改旧评分或继续修改该执行。纠错、复测都新建记录，并说明与旧记录的关系。

示例说明（仅为写法示范，不是当前故障结论）：

> 第 2 轮问“那最小值呢？”。当前附件仍为指定 Nbal 原件。实际回答要求补充字段，未继承上一轮 leak_NO3。按 F05 v2 应返回最小值 0、首次模型日序 2。已记录两轮 Run ID，请开发者核查上下文状态。

## 7. 完整示例：从文件最大值测到追问最小值

以下使用真实已知原件演示测试方法。预期不是人工验收结果，必须用自己的运行核对。

**测试目标：**验证 Agent 能读对表、算对极值，并在附件有效时理解“那最小值呢？”的字段指代。

**准备材料：**负责人提供 `Nbal_out.xls` 原件；项目中的位置为 `data/raw/whcns/received-2026-09-26/package/模型/Nbal_out.xls`。SHA-256 为 `6bf778020c6ae752da6778bc5429d1b09bc59ea1f725462dfe20207cbef88276`。在线文档中的路径不是下载链接，材料须另行分发。

1. 找到本轮任务下 `F05 v2` 的个人执行，或从用例库创建指定版本的执行并选择任务。
2. 展开通过标准及附件指纹，核对文件。若需要重置，先重置后上传。
3. 上传 Nbal 原件，确认附件状态可继续。记下 Execution ID。
4. 按 Case 原句提问；本例问“leak_NO3 最大值及对应日序”。点击“发送本轮”。
5. 对照原表，预期约 `3.65926384925842 kg N ha-1`、模型日序 `283`，数值/日序位置 `Nbal_out!C284/A284`，有效记录 `352` 条。保存第一个 Run ID。
6. 保持同一执行和有效附件，问“那最小值呢？”。预期 `0`、首次模型日序 `2`，位置 `Nbal_out!C3/A3`，共 `191` 条并列最小值，范围仍是 `352` 条。保存第二个 Run ID。
7. 核对并评分。能直接核查的证据与答案按事实判断，不能看到的内部路由/工具不要猜。
8. 提交后确认页面显示“已保存的开发试评”。在共编文档记 Case、Execution、两轮 Run、实际现象和结论。

这一过程通常有上传事件和两次提问事件，共两个问答 Run。若先重置，多一个事件也正常。模型日序 283 不能自行换算成某个公历日期；此结果是读已有输出表，未重新运行 WHCNS 模型。

若失败：把执行链接、失败轮次和证据交给开发者。若修复后复测：使用同一 Case 版本的新执行和新评分；构建变化时由开发者提供新任务。旧记录保留，开发者负责关联 Issue。

## 8. 前台聊天体验怎样测、怎样留档

输入法、Ctrl/Cmd+Enter、拖拽、滚动、复制反馈、引用跳转和多文件选择，都应在前台聊天入口测试。后台能验证 Agent 回答流程，但不会覆盖前台所有交互。

建议按以下顺序：

1. 打开共编验收文档，认领 UI01–UI07 等项目，读本轮标准。
2. 在前台创建新的会话，执行规定动作。精确记下问题原句、文件及选中状态、时间、浏览器和窗口宽度。
3. 保存实际回答、错误、截图或网络请求。没有 Run 的上传/移除动作填“不适用”；前台没有后台 Execution，填“未产生”。
4. 若页面没有显示可复制的 Run ID，请开发者用时间和原句定位；未取得就写“未取得”。
5. 结果填共编文档对应行，复杂问题填第 4 节。可以在后台手动备注中引用记录位置，但不能把备注说成系统自动证明。

UI02 历史“新对话后无法发送”目前未复现。你再次测试未发生时写“本次未复现”，不能据此写“原故障根因已经修复”。如果复现，尤其要保存是否发出请求、响应状态及新 Run 是否产生。

## 9. 领域专家如何做独立审核

本节仅适用于获配 `reviewer` 身份的人。普通测试者完成可观察的功能评价即可；审核人与材料提供者另行协作。

### 9.1 审核一份冻结回答

1. 登录自己的审核身份，打开“质量管理 → 审核队列”。
2. 按状态筛选，或检索 Case、Execution ID、测试者；找到负责人分派的执行。
3. 点“打开执行与审核表单”，核对 Case 版本、问题原句和每轮实际回答。审核旧回答时不要点新建执行替换审核对象。
4. 取得论文原文、手册、表格或运行记录，逐条核查断言，记原文页码/单元格和适用范围。
5. 在“领域专家审核”选择结论，填写审核材料路径、64 位 SHA-256 和具体依据，点“保存独立审核”。路径与指纹应由可追溯材料提供，不要填写示例假值。
6. 确认审核历史有你的身份、时间和结论。原开发试评不会被覆盖。

审核表单记录材料引用和指纹，不会自动上传材料、验证材料语义或替你阅读全文。缺原文、超出专长等情况，可在共编文档明确记“缺材料 / 超出专长”；需要在后台归档时按表单可用的“受阻”并解释原因。

“当前用例版本的审核历史”可能包含这个版本的多条记录；判断某个执行的专家结论时，同时核对审核队列中的 Execution ID，不要把其他回答的结论移用过来。

### 9.2 专家有分歧时

审核队列会显示“专家结论有分歧”。审核人应阅读各份依据，再填写“分歧处理结论”和“分歧处理依据”，保存独立处理记录；仍无法解决可选“仍待核实”。原审核不删除。新增审核后，旧处理意见不自动覆盖新出现的分歧。

“专家结论一致”只说明现有记录的结论值一致，可能一致不通过，也不表示达到了某个规定专家人数或正式发布门槛。

### 9.3 核实模型输入输出配对

“资料与证据 → 资产目录”可查看已登记资料。开发者先登记输入、输出、证明材料和候选配对；审核人选中候选配对，核对输入/输出，选择证据资产并填写依据，点“保存核实”。

文件在同一个压缩包里，或聊天里称它为玉米案例，都不足以证明输入产生了这个输出。应有实际运行包、参数、程序版本或其他可核验记录。缺材料时保留候选状态，不为了完成流程作肯定结论。

## 10. 测评的闭环与你的交付物

```text
负责人确定用例和版本
    → 开发者创建任务
    → 测评者按步骤执行，保存回答与证据
    → 测评者提交本次评分
        → 满足标准：保留结果，关键场景由开发者建回归基线
        → 明确失败：开发者登记 Issue、定位和修复
        → 无法判断：说明缺材料/环境，由相应人员补齐
    → 修复后用新执行重新测试、重新评分
    → 开发者关联复测，核验版本和结果
    → 需要专业判断的内容由专家独立审核
```

一项测试交付时，至少留下：Case ID 和版本、Task ID（如有）、Execution ID（如有）、相关 Run ID、真实原句、文件/证据位置、实际与预期差异、结论、测评者和时间。后台保存结构化证据，共编文档记录本轮人工现象、分工和协作事项，二者通过 ID 对应。

这次测完了，不等于系统已经可以正式发布。开发者还需汇总可比结果、处理问题，专业审核人核实专业结论，负责人决定交付范围。

## 11. 常见问题

| 现象 | 原因或处理办法 |
|---|---|
| 登录后菜单比别人的少 | 先看角色；普通 tester 的菜单较少是正常权限设置 |
| 找不到某人的执行 | tester 只能看自己的执行；请开发者或授权审核人协助，不共享密钥 |
| 看得到执行但没有操作/评分表单 | 可能不属于自己、已经评分、正在自动重跑，或处于审核页面；回到自己的开放执行确认 |
| 任务列表是空的 | 尚未创建任务不等于故障；正式批次请负责人先安排，探索可独立执行 |
| 页面显示临时上下文不可用 | 上下文过期或后端重启；开放执行可重置并重传。旧证据仍在，重置不会自动重放前面的问答 |
| 刷新后要求重新登录 | 当前设计如此；登录后回原地址。尚未提交的文字需重新核对 |
| 附件名称或指纹不符 | 使用指定原件，别另存后当原件上传；确需替换材料由开发者更新用例版本 |
| 评分提交失败 | 先看评分区提示，检查必选项、受阻规则、说明与证据是否完整 |
| 已评分，后来发现自己填错 | 保留旧记录，新建执行或纠正说明并交负责人处理，不直接改库 |
| 后台通过，前台仍有交互故障 | 两个入口测试范围不同，按前台真实现象另记问题 |
| 已有专家审核，却仍可能失败 | 打开审核结论；有审核记录不代表通过，也不覆盖每次新运行 |
| 重跑“结束”但没有评分 | 重跑不自动评分；需要新执行的所有者核查后提交评分 |

## 12. 开始前和结束前各核对一次

开始前：确认自己的身份、任务和 Case 版本、实际构建、指定原件，以及唯一结果记录文档。材料或环境不满足时明确标注。

结束前：确认事件和评分确实保存、失败证据能定位、ID 已登记、人工结论没有抄自动测试结果；需要修复或专家核实的事项已交给对应负责人。
