## 修复的行为

| 场景 | 原缺口 | 修复后 |
|---|---|---|
| Task 新建执行后服务更换版本 | 只在新建时核对配置，旧执行可能继续产生另一版本的 Run | 每次提问、上传、重置和移除均核对 Task；已有证据仍可查看、加手动说明和评分。历史混用配置的 Task 只能记受阻。 |
| Case 编辑内容尚未保存 | 发布按钮仍可发布先前保存的草稿 | 内容、附件选择、备注有未保存变化时禁用发布。 |
| 两人编辑同一草稿 | 发布请求未声明所核对的修订，可能发布他人刚保存的内容 | 保存与发布都核对修订。发布必填 `expected_revision`，发布结果保存 `draft_revision`。刷新列表不会更新编辑基准；重新打开修订才载入新内容。 |
| Issue 填写修复版本 | 可手填与实际 Run 不符的构建名 | 从保存的 Run 核对版本并保存 `runtime_config_versions`、`version_verified`。缺少 Run 或混用配置不能关联有效通过；受阻记录仍可保留。 |
| 问题曾通过、后来又失败 | 任意一次通过都会使问题永久计为解决 | 按最近一次复测判断；最新结论须为通过且版本已核验，才计为已解决。 |
| 问题列表展示复测 | 列表接口未返回复测，页面一直显示 0 次 | 返回按时间保存的复测记录，显示次数与核验状态，可分别打开原执行和复测执行。 |
| 输入、输出或证据文件登记后被替换 | 核实配对时只读取登记时的摘要 | 提交核实时重新计算三份原件指纹；不一致时拒绝核实，候选记录保留。 |

现有 Case、Run、Review、Issue 和审核记录不批量重写。旧复测没有版本核验字段时，不自动推断其已核验。
